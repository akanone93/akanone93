# Layer 1 — P7 to P10: functions, operations and developer experience

The nine rows of P7, P9 and P10 still `WIP` (P8 has none). They wait for the reference phone, a
Kubernetes run outside this container, a month of production-like uptime, a CI run on real
release builds, or people new to Plux. Check numbers 700–799 belong to this file.

## Resources this file adds

| ID | What | Made by |
|---|---|---|

| R-L1-HA | A production-like HA installation from the Helm chart (`deploy/helm/plux`): two or more replicas per role, CloudNativePG, replicated object storage and Valkey, with Prometheus loading `deploy/observability/rules/plux.rules.yml` and Grafana the dashboards | L1-OPS-704 |

### L1-FN-701 — A device function computes within 20 ms on the reference phone (FN-056)

- **Needs:** R-L1-MID with Plux Express (R-L1-BANK of p06)
- **Do:** in flight mode open Instalments, tap **Calculate on this device** for 3 and 6 months,
  then 999.99; time 100 calculations in the release build's performance overlay (p50, p95).
- **Expect:** the schedule appears offline; 999.99 gives `PRINCIPAL_TOO_SMALL`; p95 ≤ 20 ms.
- **Why:** device functions must feel instant; the 4 MiB module limit is a registry limit, checked on the host (FN-056).
- **Look at:** item F2 of `docs/security/real-device-checklist.md`; the numbers decide WAMR against `wasmi` (ADR-0011).
- **Moves to DONE when:** the numbers are in "Device numbers" of `docs/benchmarks/p7-functions.md` and within budget.
- **Result:** ☐ pass ☐ fail — notes:

### L1-OPS-702 — HA install, rolling upgrade and failover (DEP-004)

- **Needs:** R-L1-KIND
- **Do:** `make e2e-kind`; during its rolling upgrade, watch `kubectl get pods -A -w` in a second terminal.
- **Expect:** the script ends without an error: two replicas per role, three PostgreSQL instances,
  `helm test` green after install, upgrade and the Valkey and PostgreSQL failovers; an old pod

- **Moves to DONE when:** the `e2e-kind` CI job (`.github/workflows/ci.yml`) has run green, or your run here passed; it never ran in the agents' container.
- **Result:** ☐ pass ☐ fail — notes:

### L1-OPS-704 — 99.95% monthly availability of manifest and control (NFR-040)

- **Needs:** R-L1-HA (made here: `helm upgrade --install` as `docs/guides/operations.md` says), with real or synthetic device traffic
- **Do:** run it for a calendar month; open the Grafana dashboard **Plux SLO burn**.
- **Expect:** the manifest error ratio over the month stays under 0.05% (about 21 minutes of errors).

- **Moves to DONE when:** one month's figure from a real HA installation is recorded; no CI job can
  show it. A month of an operator's production data serves too.
- **Result:** ☐ pass ☐ fail — notes:

### L1-DEV-705 — The Dev app installs and previews on both platforms (DEV-001)

- **Needs:** R-STACK; make R-L1-DEVAPP
- **Do:**
  1. In `schema/testdata/documents/starter` run `plux dev`; pair both phones by **Scan QR**.
  2. Edit a page and save; run `plux dev` in a fixture under `schema/testdata/documents` whose
     pages use an optional package (maps, charts, media, scanner) and open one.
  3. `plux dev security-detect root`, then `plux dev logs`.
- **Expect:** both apps pair and render the edit; the optional package's widget renders; the
  detection appears in the dev stream and R-L1-DEVLIST shows the device's level unchanged.
- **Why:** the Dev app previews any plugin, and its `plux_security` only reports (DEV-001, ADR-0091).
- **Moves to DONE when:** both platforms' outcomes are noted, and the CI run on real Gradle and
  Xcode builds (the dispatched run of the P10 hand-off) is green.
- **Result:** ☐ pass ☐ fail — notes:

### L1-SYN-707 — Background sync stages a release, never activates it (SYN-014)

- **Needs:** R-STACK, R-L1-MID, R-L1-IPHONE, the starter app (`apps/starter`) built with
  `PluxConfig(backgroundSync: BackgroundSyncConfig(enabled: true))` and, on iOS,
  `dev.plux.backgroundSync` under `BGTaskSchedulerPermittedIdentifiers` in `Info.plist` (no host app enables it today)
- **Do:**
  1. Open the app, send it to the background, publish a new release.
  2. Android: find the job with `adb shell dumpsys jobscheduler | grep -A3 <application id>`, run it
     with `adb shell cmd jobscheduler run -f <application id> <job id>`. iOS: pause in Xcode and run
     `e -l objc -- (void)[[BGTaskScheduler sharedScheduler] _simulateLaunchForTaskWithIdentifier:@"dev.plux.backgroundSync"]`.
  3. Bring the app back, then restart it in flight mode.
- **Expect:** step 3 still shows the old release until the restart; the restart shows the new one with no network.
- **Why:** updates are ready at the next start without surprising the user (SYN-014, ADR-0092).
- **Moves to DONE when:** both platforms pass here and the native tests ran green in CI.
- **Result:** ☐ pass ☐ fail — notes:
