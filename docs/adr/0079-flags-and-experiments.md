# 0079. Feature flags and experiments: `Variant` nodes, assignment, exposure and sequential analysis

- **Status:** Accepted
- **Date:** 2026-10-18
- **Requirements:** `ABT-001`, `ABT-002`, `ABT-003`, `ABT-004`, `ABT-005`, `ABT-006`, `ABT-007`, `NAV-009`, `ANL-001`

## Context and problem

Teams want to ship a change to a share of users, measure it and keep the winner, and to switch
features by segment without a release. Plux apps are server-driven and signed, so variants must
be part of a verified release, not downloaded code (`SEC-054`). Experiment statistics are easy
to get wrong: peeking at results inflates false positives. The questions: how are variants
represented, where is a user assigned, when is exposure recorded, how are results analysed, and
how does a winner become the app?

## Decision drivers

- Variants are in the release; no downloaded executable code.
- Assignment must work offline and stay sticky.
- Exposure must mean "the user was shown it", not "was assigned".
- Valid inference under continuous monitoring.
- The winner must produce the same bytes as a document written with the winner (`CMP-002`).
- User attributes leave the device only hashed.

## Considered options

1. A `Variant` node and `experiment.<key>` bindings in the document model; device-side assignment; mSPRT confidence sequences; compiler-pass promotion.
2. Fixed-horizon tests (t-test, z-test) evaluated when the planned sample is reached.
3. A third-party experimentation service evaluating on its servers.

## Decision

Chosen option: **1** (maintainer decisions Q10, Q11, Q12).

- **Flags (`ABT-006`).** Typed: bool, number, string, JSON with a schema (`PLX-1701` for an
  unknown type, `PLX-8203` for a refused type change). Defaults live in the app document,
  per-segment values in the control document (ADR-0077). PXL reads `flags.<key>`; host accessors
  are generated by `plux codegen`; values change without a release. `NAV-009` flag guards
  evaluate targeting.
- **Experiments (`ABT-001`).** Scope: page, component subtree (`Variant` node), prop value
  (`experiment.<key>.<prop>` in PXL), flow (route mapping) or plugin version (channel split).
  Control plus variants, allocation, targeting, schedule, primary and guardrail metrics, minimum
  sample size. A `Variant` without control gives `PLX-1702`; weights not summing to 100,
  `PLX-1703`.
- **Assignment (`ABT-002`).** `variant = weightedPick(sha256(experimentSalt || subject))`, on the
  device, sticky. The exposure event is recorded only when the variant's node builds, through a
  renderer hook, not at assignment.
- **Layers and holdouts (`ABT-004`).** Layers partition traffic so experiments in one layer are
  mutually exclusive (`PLX-8200` on overlap); a global holdout excludes a fixed share from all.
- **Analysis (`ABT-003`).** Rollups by variant from ADR-0080; always-valid confidence sequences
  (mSPRT with a normal mixture) for proportions and means; a chi-squared sample-ratio check at
  p < 0.001 flags the experiment (`PLX-8202`); CUPED with the 14 days before exposure as the
  covariate where it exists. In-house. Validated on simulated A/A and A/B data with known
  effects; type I error stays at or below alpha under continuous peeking (tested).
- **Promotion (`ABT-005`).** `plux experiment promote <id> <variant>` creates a release whose
  compiler pass replaces each `Variant` by the winner's subtree and inlines `experiment.<key>`
  bindings (`PLX-2301`; `PLX-2300` unknown key, `PLX-2302` node budget).
- **Approval (`ABT-007`).** Experiments on `secure` pages or money flows under `maximum` go
  through ADR-0076.

## Consequences

- **Positive:** results can be read at any time without inflating errors; assignment needs no
  network; the promoted release is deterministic and contains no experiment machinery.
- **Negative:** the document model, compiler and renderer each gain a node and a pass; mSPRT
  needs larger samples than a fixed-horizon test for the same power; the statistics are in-house
  code that needs thorough simulation tests.
- **Follow-up:** `Variant` table in `schema/` (before 0.0.1, additive); migrations 0036 to 0038;
  documented interpretation of confidence sequences; guides in E11.

## Options in detail

### Option 1 — `Variant` nodes, device assignment, mSPRT

Everything is verified and shipped in the release; the control document only carries
allocations. Statistics are always valid, which matches dashboards people refresh daily.

### Option 2 — fixed-horizon tests

Simpler and more powerful at the planned sample size, but invalid if anyone looks early, which
dashboards invite. Would need enforced "no peeking" UI. Rejected.

### Option 3 — third-party service

Sends user and exposure data to an external party and adds an SDK; conflicts with the egress
rules and offline use. Rejected.
