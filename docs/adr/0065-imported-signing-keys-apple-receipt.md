# 0065. Imported signing keys and Apple's fraud-metric receipt

- **Status:** Proposed
- **Date:** 2026-10-13
- **Requirements:** `SEC-123`, `SEC-007`, `SEC-120`

## Context and problem

`AL3` on iOS needs Apple's fraud-metric receipt for the attested key at or below the
profile's `riskMetricMaxAL3` (`SEC-007`). Apple's receipt service authenticates the *app
developer* with an ES256 JWT signed by the developer key (a `.p8` file, PKCS#8 EC P-256),
issued by Apple, with a key ID and the Team ID. Until now every key `signing/` held was
generated by Plux inside its backend ([ADR-0060](0060-signing-backends-and-audit-checkpoints.md)).
This key is generated by Apple and given to the operator: it must be *imported*, and
afterwards used without ever leaving the signing abstraction (`SEC-120`, `SEC-123`).

## Decision drivers

- The key never leaves `signing/` in clear (only `signing/` touches private keys, L-1).
- Prefer a backend that cannot export it (HSM, Vault Transit).
- Works on every deployment, including one with the file-based or no-import backend.
- Off by default; without the key iOS stays at `AL2`.
- Testable without Apple.

## Considered options

1. Keep the `.p8` file as configuration read by the receipt client.
2. Import into the configured backend as a non-extractable key; where the backend cannot
   import, an `imported` backend that stores an envelope-encrypted key (chosen).
3. Skip `AL3` on iOS.

## Decision

Chosen option: **2**.

**Import.** An operator imports the `.p8` once, with `plux-server keys import` (or the admin
API with step-up), naming the role (`apple-appattest-receipt`), the key ID and the Team ID.
The PKCS#8 bytes are parsed and validated (EC, P-256; otherwise `PLX-6081`), then:

- **PKCS#11** (through `plux-pkcs11-helper`): `C_CreateObject` with `CKA_SENSITIVE=true`,
  `CKA_EXTRACTABLE=false`, `CKA_SIGN=true`. After import the helper can sign but not export.
- **Vault Transit:** the import endpoint, with the key marked non-exportable and
  non-deletable by default.
- **Backends without import** (file-based development, KMS products that offer no import
  for this key type): the **`imported` backend**. It holds the key *envelope-encrypted*: the
  PKCS#8 is encrypted with AES-256-GCM under a data key, and the data key is wrapped by a
  wrapping key the configured backend holds and does not export. The encrypted envelope is
  stored in PostgreSQL with the role, key ID and a digest of the public key. Per operation,
  `signing/` unwraps the data key through the backend, decrypts the key into a buffer owned
  by `signing/`, signs and zeroes the buffer. The key is never logged, returned, cached
  beyond the call or visible to any other package.

The plaintext file is deleted by the operator after import; the import tooling says so.

**Scope in P7.** P7 delivers the `imported` backend over every configured backend (its
`Crypter` holds the wrapping key, so the HSM or Vault still guards the key at rest). Native
import into PKCS#11 and Vault Transit, which keeps the key out of process memory entirely, is
the preferred path where available and follows as its own change; until then the decrypted key
exists only inside `signing/` for the duration of one signature.

**Where it runs.** Registration and re-attestation run on the `api` role, which holds no signer
(L-3). The device service is therefore given an adapter that signs with the `apple-appattest-receipt`
key only and refuses every other role; Apple's call is bounded to 3 s, after which the device
registers at `AL2` (`PLX-6080`) rather than wait. The JWT travels as `Authorization: Bearer <jwt>`,
the request body is the base64 receipt, and the default root pool is the App Attestation root —
the three points the maintainer's first run with the real key confirms.

**Receipt client.** For the iOS attested key it requests Apple's fraud-metric receipt,
signed with **ES256** in a JWT (`kid` is the key ID, `iss` the Team ID, `iat` current time,
short expiry), against `data.appattest.apple.com` in production and
`data-development.appattest.apple.com` for development attestations (chosen by the
attestation's environment). The server keeps the receipt and refreshes it before Apple's
validity ends; the risk metric is read from the receipt and mapped to `AL3` when it is at or
below `riskMetricMaxAL3`. Apple's response is untrusted until the receipt's signature chain
verifies against Apple's roots (`SEC-007`). A failure to reach Apple, an expired or invalid
receipt is `PLX-6080` (`FRAUD_RECEIPT_UNAVAILABLE`) and leaves the device at `AL2`, never
raises it. An unusable imported key is `PLX-6081` (`IMPORTED_KEY_INVALID`).

**Off by default.** The feature is a setting; without it, or without a key, iOS devices stay
at `AL2` and a policy that requires `AL3` on iOS reports `PLX-6002`. Plugging in the real
key needs configuration only.

**Simulator.** A local simulator of Apple's service (a Go test server, with the same
paths, JWT checks and a receipt signed by a test root) runs in CI so every path is tested
without Apple credentials: valid, expired and tampered receipts, wrong key ID or Team ID,
the production and development hosts, outage.

## Consequences

- **Positive:** the only externally issued key is held like Plux's own; an operator with an
  HSM keeps the key non-extractable; any deployment can use the feature; iOS `AL3` becomes
  reachable without changing the architecture.
- **Negative:** one more backend and a new storage table to maintain; on backends without
  import the key exists in clear in memory for the duration of a signature, which is the
  cost of not having a hardware boundary and is documented as such; the real Apple
  interface cannot be exercised in CI.
- **Follow-up:** `signing/` gains the import operation and the `imported` backend; the
  runbook records the import, rotation and revocation of the Apple key; the operator
  documentation states that an HSM or Vault Transit is recommended.

## Options in detail

### Configuration file read by the receipt client

Simple, and the private key sits in a file readable by the process that talks to the
internet, outside the signing abstraction. Rejected: violates L-1 and `SEC-120`.

### Import into the signing abstraction

The key travels once, at import, and is then covered by the same rules, audit and backends as
every other key. The `imported` backend closes the gap where a backend cannot import.
Chosen.

### No `AL3` on iOS

No work and no Apple dependency, but iOS devices could never reach the highest assurance
level the specification defines. Rejected by the maintainer (C1).
