# P10 — The dev loop

Results of Phase 10's edit-to-device benchmark, with its method (DoD-4, `QA-007`). `DEV-010` and
`NFR-030` budget 500 ms at the 95th percentile from a file save to the changed page on the
device, over the netsim good-Wi-Fi profile, with the server part reported separately. The budget
is split in two measurements that add up: the server and the transport at most 350 ms, the
device's apply at most 150 ms. Every number below comes from this repository's cloud container
(Intel Xeon @ 2.10 GHz, 4 cores, Linux x86-64; 2026-10-23), which other jobs were using at the
same time (load average 5 to 8 on 4 cores); not from a phone or the reference deployment.

| Requirement | Target | Command |
|---|---|---|
| `NFR-030`, `DEV-010` | Server and transport: ≤ 350 ms p95 | `make bench-devloop` |
| `NFR-030`, `DEV-010` | Device apply of a one-page change: ≤ 150 ms p95 | `make bench-devapply` |

## Server and transport (`make bench-devloop`)

**Method.** `TestDevloopEditToDeviceLatency_NFR_030_DEV_010`
(`backend/internal/devsession/devloop_bench_test.go`), run with `PLUX_BENCH_DEVLOOP=1` and a
`PLUX_TEST_DATABASE_URL`; without the variable it skips. The project is the conformance project
with 48 copies of its calculator page, 100 nodes each (50 pages, generated by
`incrementaltest.ManyPages`, the generator of the incremental compiler's own latency test). A
simulated device pairs, then opens the real `/dev/socket` (ticket and DPoP proof verified as in
production) through a `netsim` forwarder with the `good_wifi` profile (30 Mbit/s down, 15 Mbit/s
up, 20 ms RTT), says hello and parses every frame with `protojson`, as the Dart channel parses
it. 5 edits warm the draft, the compiler's cache and the connection; then 200 edits, each a
`replace` of one Text node's expression on one page, go through `Service.PushPatch`. The clock
starts when `PushPatch` is called (the save) and stops when the device has parsed the bundle
frame with that bundle's sequence.

| Part | What it times |
|---|---|
| `server` | Compile, sign and deliver, the `PushPatch` timings (`NFR-030`: the server part) |
| `admit` | The rest of the call: authorisation, session and limits, patching the draft, the audit entry |
| `transport` | From `PushPatch` returning to the device having parsed the frame: the socket writer, the simulated network, the parse |
| `total` | `server` + `admit` + `transport`; gated at 350 ms p95 |

The test prints the parts as JSON (p50, p95 and maximum, in milliseconds) and fails when the
`total` p95 exceeds 350 ms.

## Device apply (`make bench-devapply`)

**Method.** `packages/plux_flutter/test/devtools_api/dev_apply_bench_test.dart`, run with
`PLUX_BENCH_DEVAPPLY=1`. A signed dev bundle that changes one page (the conformance loans
plugin with a page swapped, alternating with the original so that every apply changes exactly
one page) goes through `DevOverlayApplier.apply`: signature against the development root (pure
Dart Ed25519), hashes, the overlay store's write, the switch of the active release. 10 warm-up
applies, then 200 timed. The host is the Flutter test VM, not a phone: the figure is an upper
bound for the verification and a lower bound for rendering, which the benchmark does not
include.

| Run | p50 (ms) | p95 (ms) | Maximum (ms) | Budget p95 (ms) |
|---|---:|---:|---:|---:|
| 1 | 15.6 | 29.1 | 40.7 | 150 |
| 2 | 14.2 | 20.5 | 107.8 | 150 |
| 3 | 22.2 | 48.8 | 84.1 | 150 |

**Verdict: the device's budget is met on this host with a margin of 3x or more.**

## Results of the server and transport

A first version of the benchmark edited the page's `description`. The compiler does not put it
in the bundle, so the push carried a 1.7 KB frame and the total p95 was 92 to 107 ms; it said
nothing about a real edit and was replaced by an edit of a node's expression, which changes the
page section and with it the plugin bundle.

One run of 200 edits, with the real edit:

| Part | p50 (ms) | p95 (ms) | Maximum (ms) |
|---|---:|---:|---:|
| `server` | 59.8 | 113.3 | 470.9 |
| `admit` | 3.2 | 6.4 | 14.6 |
| `transport` | 506.4 | 526.1 | 560.7 |
| `total` | 572.6 | 618.7 | 979.9 |

**Verdict: the 350 ms budget is not met.** The reading:

- **The server is fast.** Compile, sign and deliver take 60 ms at p50 and 113 ms at p95, within
  the 100 ms the compiler alone is budgeted (`CMP-051`) plus signing.
- **The transport is the whole bundle.** An edit of one page changes the plugin bundle, and the
  dev bundle frame carries every bundle the device does not hold yet: 1.53 MB of JSON for the
  50-page plugin, 100 nodes a page. At 30 Mbit/s that takes about 410 ms before the 10 ms of
  latency and the write; the frame is not compressed on the socket.
- **Compression would meet the budget.** As a diagnostic, not part of this change, enabling
  permessage-deflate on both ends of the socket (`websocket.CompressionContextTakeover`) and
  repeating the benchmark with 60 edits gave `transport` p50 89 ms and p95 97 ms, and `total`
  p50 155 ms and p95 168 ms. The alternative is a smaller frame by design (sending the changed
  page section, not the plugin bundle). Either is a change to the dev socket's protocol
  (ADR-0087), which belongs to the maintainer.
