## 1. Goal and exit criteria

**Goal (spec §5.1, as changed by §2).** P7 delivers Plux Functions:

- an interface-only **Rust** SDK and a reproducible Rust-to-WebAssembly build pipeline
  (`wasm32-wasip1`), post-processed with `wasm-opt`, with input and output schemas derived
  from the Rust types, recorded provenance and signed artifacts (§2.1 D1);
- a **builder** role that builds functions from source with vendored dependencies and no
  network, so that the provenance and signature are the server's, not the developer's
  machine's (D3);
- immutable function versions, aliases, and app releases that record the resolved version
  of every function they reference;
- the `fnrunner` role on `wazero`: modules compiled ahead of time at deploy and cached, a
  fresh instance per invocation, limits from the registry, deny-by-default capabilities, no
  database credentials or signing keys, network only through an **egress proxy** that
  enforces each function's allowlist (D5);
- **on-device execution** in an interpreter-only engine embedded through FFI, off the UI
  isolate, cancellable, with the plugin's device functions shipped as one module inside its
  signed bundle (D2);
- server invocation through `FunctionService.Invoke` with DPoP, the required assurance level,
  attestation binding and SCA where declared, idempotency keys, rate limits and quotas, and
  business errors kept apart from system errors;
- the `invokeFunction` action wired end to end, with the compiler checking placement,
  capabilities and the input and output types;
- `plux fn` (`new`, `build`, `test`, `deploy`, `alias`, `invoke`, `logs`) and per-function
  metrics, logs and traces;
- the P6 carry-overs of §2.2.

**Exit criteria.**

1. The spec's criterion: the loan calculator runs on the device offline and on the server
   with a trusted result; limit, fuzz and isolation tests pass on both placements; the
   latency targets are met — on the server in CI (`FN-023`, `NFR-022`), on the device on
   the reference device later (`FN-056` stays `WIP`, §3.2).
2. Definition of Done (spec §5.3) DoD-1 to DoD-9 holds, with the deferrals of §3.2. DoD-6
   for P7 means the threat-model delta for functions (a new trust boundary: untrusted code
   on the server) and the MASVS/ASVS checks it touches, with evidence.
3. Plux Bank uses a server-placed function for a trusted calculation (fee or eligibility)
   behind SCA; Plux Express uses a device-placed function for a live offline calculation
   (DoD-8).
4. Every milestone passes the milestone exit gate (§11).
5. The core package stays within its size budgets (`RT-061`, ADR-0036 as revised
   2026-10-12): the device engine's library and the FFI glue are measured in F5, and the
   choice of engine (D2) is made with those numbers.
6. No P3–P6 budget regresses beyond the A/B gate (startup, sync, DPoP).

| **D5** | **Egress proxy (`FN-013`): our own**, a small Go HTTP(S) forward proxy on the standard library, as its own role (`egress`). It enforces the per-function domain allowlist, refuses private addresses (the gateway's SSRF rules), and is the only route out of `fnrunner`. No new dependency. |
| **D6** | **Approvals before P9 (`FN-007`, `FN-055`):** until the approval engine (`GOV-020`, P9) arrives, deploying a function to production and enabling device placement under `maximum` require a new RBAC permission with step-up (the stand-in already used for release promotion, `rbac.go`). The spec text of both says so; P9 replaces the stand-in. |
| **D7** | **Studio and Dev-app parts move:** "runnable in Studio" (`FN-031`) moves to P11; "available in Studio" and "device invocations appear in dev-session traces" (`FN-032`) move to P11 and P10. | **D8** | **Function key-value store (`FN-002`, `FN-012`):** on the server, PostgreSQL with one namespace per app and function, under row-level security like every tenant table, bounded by limits from the registry; `fnrunner` reaches it only through a host call served by the `api` side (it holds no database credentials). Device functions use the plugin's existing key-value namespace. |
| **D9** | **`wasm-opt` (Binaryen)** joins the allowlist as a pinned build tool, after F1 shows its output is byte-identical across runs (`CMP-002`, `CI-006`). |
| **D10** | **Rust is used only for Plux Functions.** An analysis of the device and the server against the measured budgets (2026-10-13) found no other place where Rust is worth its cost: rendering is Flutter's, sync is network-bound, the heavy primitives are already native (zstd, SQLite, platform AES, hardware keys), PXL and action steps are within budget and an FFI call per binding costs what it would save, and the server meets its budgets in Go. One item to measure, not act on: the Studio PXL language service (`PXL-008`, P11) is meant to be Go compiled to WebAssembly for the browser; P11 measures its size first. |

### 2.3 Why Rust (measured 2026-10-13)

The same function — a 360-month loan schedule, JSON in and out — built with Go 1.27
(`GOOS=wasip1`, `go:wasmexport`, `-ldflags=-s`) and Rust 1.97 (`wasm32-wasip1`,
`opt-level="s"`, LTO, `panic=abort`), neither through `wasm-opt`, run on `wazero` 1.11 on an
x86-64 CI-class machine. The interpreter stands in for the device engine; real phones are
slower for both, the ratio is structural (Go's runtime and collector are in every module).

| | Go | Rust | Spec |
|---|---|---|---|
| Module, raw / gzip | 4.37 MB / 1.20 MB | 82 KB / 35 KB | ≤ 4 MiB per plugin (`FN-056`) |
| Interpreter: fresh instance | 14 ms | 0.13 ms | — |
| Interpreter: one call (p50 / p95) | 85 / 113 ms | 11 / 15 ms | ≤ 20 ms p95 on the device (`FN-056`) |
| Compiled: compile at deploy | 2.0 s | 0.05 s | ≤ 50 ms first call after deploy (`FN-023`) |
| Compiled: fresh instance | 4–6 ms | 0.25 ms | ≤ 1 ms warm overhead p99 (`FN-023`), fresh instance per call (`FN-010`) |
| Compiled: one call | 4.6 ms | 0.8 ms | — |
| Linear memory | 4 MiB | 1.2 MiB | 32 MiB device default (`FN-053`) |
| Build, clean / incremental | 5.6 s / 0.3 s | 7.9 s / 1.8 s | — |

A decimal variant (Go `math/big`, Rust `rust_decimal`) showed 1 s against 36 ms in the
interpreter; part of that gap was the Go code, so it is not counted. TinyGo, the usual way to
small Go modules, was rejected in the spec already: its `reflect` support is partial and
`encoding/json` panics at run time under WASI. The cost of Rust — a harder language for
function authors, a second toolchain in CI and the builder — is accepted for the margin.

**E5 — Functions and modules.**

- A function is one Rust crate in `functions/<name>/` of the project, beside its document
  `function.json` (kind `function`). The document is the single source of the name,
  placement, capabilities, limits, required assurance, attestation and SCA flags, `pure` and
  TTL, and test cases. The schemas are derived from the Rust types (`FN-004`), never written
  in the document.
- The SDK is two crates in `sdk/fn/`: `plux-fn` (the `Context` traits, `ServerContext` and
  `DeviceContext`, typed `BusinessError { code, message_key, params }`, the guest side of the
  ABI) and no procedural macro of our own; this replaces the attribute macro sketched in §5.1. A crate exports its handler with the declarative
  `plux_fn::function!(handler)`; the handler's context type fixes its placement at compile
  time (a device handler cannot reach `http`, `secret` or `claims`, `FN-008`, `FN-052`).
- **Every module is linked by a generated wrapper crate**, `plux-module`, which depends on
  one or more function crates and emits the ABI exports with a dispatch table: a server
  function version is a module of one function; a plugin's device module links all its
  device functions (`FN-051`). The wrapper asserts each crate's placement against its
  document, so a mismatch fails the build (`PLX-7205`).
- Schemas: the wrapper built with the feature `plux-schema` exports `plux_schemas`; the
  builder runs that module in `wazero` to read the input and output JSON Schemas, then builds
  the artifact without the feature. User code never runs natively in the builder beyond
  allowlisted build scripts and procedural macros.
- Versions are integers per function, app and environment, assigned at deploy, immutable;
  aliases are `^[a-z][a-z0-9-]*$`, as in `FunctionGrant`. A release records name, version,
  module SHA-256 and placement of every referenced function; a device invocation sends the
  version its release pinned, and the server refuses a version no active release of the app
  pins.

**E6 — ABI v1 (ADR-0062, `docs/functions/abi.md`).**

- Exports: `memory`, `plux_abi_version() -> i32` (1), `plux_alloc(len i32) -> i32`,
  `plux_invoke(index i32, ptr i32, len i32) -> i64`. The result is packed
  `(ptr << 32) | len` and points to `tag byte || UTF-8 JSON`: tag 0 the output, tag 1 a
  business error `{code, messageKey, params}`, tag 2 the guest refused its input
  (`PLX-7008`), tag 3 it could not encode its output (`PLX-7009`). A fresh instance per call
  means no `plux_free`. A trap or a limit is a system error, classified
  by the host.
- Imports from module `plux_v1`, each returning `i32` status or `i64` packed result, negative
  for a status: `log(level, ptr, len)`, `clock_now() -> i64` (Unix ns), `context() -> i64`
  (JSON: app, environment, placement, assurance level), `env_get`, `kv_get`, `kv_put`,
  `kv_delete`, and on the server only `http_request` (JSON request and response, body
  base64), `secret_get`, `claims`, `invoke_function`. Statuses: −1 not found, −2 capability
  denied, −3 limit exceeded, −4 egress refused, −5 upstream failed, −6 invalid argument,
  −7 unavailable. Host-returned buffers are allocated with `plux_alloc`.
- A device host refuses a module that imports a server-only function (`PLX-7018`); every
  host refuses unknown imports and an unsupported `plux_abi_version` (`PLX-7017`).
- WASI (`wasm32-wasip1`): no preopened directories, no arguments, no environment, no sockets;
  `fd_write` to 1 and 2 becomes `log`, bounded by `function.logBytes`; `clock_time_get` reads
  the host clock; `random_get` reads the host's CSPRNG; everything else returns `ENOSYS` or
  `EBADF`.

**E7 — Builds (ADR-0063).** `cargo build --release --locked --offline --frozen` with
`cargo vendor` sources, `opt-level = "s"`, `lto = true`, `codegen-units = 1`,
`panic = "abort"`, `strip = true`, `--remap-path-prefix` for every path,
`SOURCE_DATE_EPOCH`; then `wasm-opt -Os` with pinned Binaryen. The toolchain is pinned in
`sdk/fn/rust-toolchain.toml` (Rust 1.97.0). The builder runs each build in a child process
with a new network namespace (no interfaces but loopback) and resource limits; where the
kernel refuses namespaces the builder refuses to build unless `builder.sandbox: none` is set
for development, which logs a distinct warning (secure default). The artifact statement —
module SHA-256, schema SHA-256s, provenance (`FN-005`) — is canonical JSON signed through
`signing/` with the new `function` key role; the worker asks for the signature, the builder
holds no key.

**E8 — Server roles (ADR-0064).** `api` → `fnrunner` through the internal
`FunctionRunnerService` (mutual TLS), carrying the artifact reference, input, limits,
granted capabilities, verified claims and a per-invocation grant (opaque, ≤ 60 s, scoped to
app, environment, function and version). `fnrunner` → `api` through the internal
`FunctionHostService` for modules (by SHA-256), the KV, secrets (the environment's server-held
values, ADR-0061, granted per function by name) and nested invocations, each authorised by the
grant. `fnrunner` → `egress` for HTTP: every request, plain HTTP included, is a `CONNECT` tunnel
over the mutual-TLS link (refined at W2: the proxy parses no HTTP beyond `CONNECT`, and TLS to
the upstream stays end to end); `fnrunner` sends the function's allowlist with each request and `egress` also
applies the gateway's SSRF rules after resolving the name. Internal protos live in
`proto/plux/internal/fn/v1/`.

**E9 — Device engine packaging.** WAMR lives in the optional package
`packages/plux_functions` (`RT-060`), an FFI plugin built from vendored C with the same
approach as `plux_native`; the host registers it like the other optional packages. An app
without it pays nothing in size, and a device-placed `invokeFunction` fails with `PLX-5401`
(`DEVICE_PACKAGE_MISSING`). This refines §5.5 ("in `plux_native`").

**E10 — Pinned tools and sources.** `wasm-opt` is Binaryen `version_132` (released
2026-08-13) taken from the npm package `binaryen@132.0.0`, pinned by its integrity hash and run
with the pinned Bun: one platform-independent (Emscripten) build on developer machines, in CI
and in the builder image, so the optimiser's output cannot vary by host. WAMR is 2.4.3; its
interpreter subset is vendored with a SHA-256 list of every file, and a CI step compares that
list with the upstream `WAMR-2.4.3` source archive (this session could not reach GitHub
releases, so the copy came from the crates.io package `wamrx-sys` 0.3.0). The SDK uses
`serde` 1, `serde_json` 1, `schemars` 1.2; the loan example uses `rust_decimal` 1.43.

## 5. Architecture

### 5.0 Starting point (surveyed 2026-10-13)

- `wazero` runs the image codecs in `backend/internal/wasmrt`; `fnrunner` is a named role in
  `config.go` that `validate.go` refuses ("arrives in P7").
- `schema/actions/invokeFunction.json` (id 28, P7) exists; the plugin and app schemas carry
  `functions` grants (`FunctionGrant` in the bundle's FlatBuffers); the limit
  `bundle.deviceFunctionModuleSize` exists; the setting `defaultFunctionAssurance` exists.
- No function proto, no SDK, no ABI, no builder, no runtime on either side. `docs/functions/`
  holds a stub README.
- The device has native code in `packages/plux_flutter/native/plux_native.c` (mmap, zstd,
  the platform AES bridge), built for Android and iOS; WAMR joins it.
- The gateway's middleware already enforces DPoP, assurance, user identity and SCA; function
  invocation reuses it.

### 5.1 SDK and ABI (F1) — ADR-0011, ADR-0062

- The ABI is language-neutral and identical on both placements (`FN-015`): the module exports
  `plux_abi_version`, `plux_alloc`, `plux_invoke(function_id, ptr, len)`; inputs and outputs
  are JSON (UTF-8); the host imports are `log`, `clock_now`, `kv_get/put/delete`,
  `http_request` (server only), `secret_get` (server only), `claims` (server only),
  `invoke_function` (server only, depth-limited). A capability not granted fails with a
  defined error, never a trap the host cannot classify.
- The Rust crate `sdk/fn` gives a typed handler (`#[plux::function(name, placement)]`), a
  `Context` with the capabilities of `FN-002`, typed business errors with a code and a
  message key (`FN-022`), and schema derivation from the input and output types.
- `docs/functions/abi.md` and a guide; conformance vectors under `schema/testdata/functions`
  that both hosts run.

### 5.2 Build, provenance and versions (F2) — ADR-0063

- `plux fn build`: vendored crates (`cargo vendor`), `--locked`, `--offline`, pinned
  toolchain, `wasm-opt`, deterministic output checked by building twice (`CMP-002`).
- The `builder` role: receives source and vendor archives, builds in a sandbox with no
  network and bounded CPU, memory and time, writes the module, the schemas and the
  provenance (`FN-005`: source hash, dependency list, toolchain, build time, builder
  identity), and the worker has `signing/` sign them.
- Versions are immutable; aliases point to versions (`FN-006`); a release records the
  resolved version of every function its plugins reference, and a release with an
  unresolved or failing-tests function is refused.

### 5.3 Server runtime and isolation (F3, F4) — ADR-0064

- `fnrunner`: compiles modules ahead of time at deploy and caches them; a fresh instance per
  invocation; limits from the registry enforced by `wazero` (memory pages, fuel or context
  deadline, output size) and by the host (calls, depth).
- Capabilities deny-by-default (`FN-012`); HTTP only through the `egress` role with the
  function's allowlist (D5); secrets read through `signing/`-free secret storage the role is
  granted; the KV through host calls served by `api` (D8).
- `fnrunner`, `builder` and `egress` hold no database credentials and no signing keys
  (L-4, `FN-013`); mutual TLS between roles (`SEC-043`); Compose and the Helm chart gain the
  roles.
- Isolation tests: memory and time exhaustion, output flood, call-depth loops, attempts at
  filesystem, sockets and environment, cross-tenant KV access, fuzzed inputs.

### 5.4 Invocation (F4)

- `FunctionService.Invoke` on the gateway's middleware: DPoP and token, required assurance
  (`defaultFunctionAssurance` when undeclared), attestation binding and SCA where the
  function declares them (`FN-020`), idempotency for 24 h (`FN-021`), rate limits and quotas
  per function, app and device (`FN-024`), business and system errors (`FN-022`).
- Traces link the server invocation to the calling device request (`FN-032`).

### 5.5 Device runtime (F5)

- WAMR interpreter in `plux_native`, behind a Dart FFI binding; invocations run on a worker
  isolate, never the UI isolate, with the device limits (500 ms, 32 MiB) and cancellation
  (`FN-053`); the plugin's single module is loaded from the verified bundle section
  (`FN-051`, `SEC-052`).
- Only `log`, `clock` and the plugin's key-value namespace (`FN-052`); a device result is
  never sent as evidence (`FN-054`); placement disabled under `maximum` unless enabled with
  the D6 permission (`FN-055`).
- Size and speed measured for WAMR and `wasmi` on the emulators (D2).

### 5.6 Compiler and action (F6)

- The compiler resolves function references and aliases, checks placement against requested
  capabilities (`FN-008`), checks `invokeFunction` inputs and outputs against the published
  schemas (`FN-004`, `ACT-001`), and packs the device module per plugin.
- The runtime's `invokeFunction` handler dispatches by placement: the device engine, or
  `FunctionService.Invoke` through the existing client with DPoP.

### 5.7 CLI, tests and observability (F7)

- `plux fn new | build | test | deploy | alias | invoke | logs`; `plux fn test` runs the
  Rust tests natively, then the stored cases against the module on `wazero` and, for device
  functions, on WAMR, failing on any difference (`FN-030`, `FN-031`).
- Metrics (invocations, errors by kind, latency percentiles, memory peak, cache hits) and
  logs in Prometheus (`FN-032`), catalogued in Appendix G.

### 5.8 P6 carry-overs (F8)

C1 (imported-key backend, receipt client, Apple simulator, `AL3` mapping on iOS, off by
default), C3 (WebSocket pinning), C4 (SMS User Consent in `OtpInput`), C2's documentation if
not done in F0.

## 10. Risks

| Risk | Mitigation |
|---|---|
| Rust is hard for function authors | A small SDK surface, templates from `plux fn new`, the loan calculator and a fee engine as examples, clear compiler errors surfaced by the builder |
| WAMR misses the device budgets or the size budget | D2's side-by-side numbers in F5; `wasmi` as the alternative; the module limit stays in the registry |

## 11. Process

- **Branch and pull request:** one branch, `feat/phase-7`, and one pull request at the phase
  exit, with the F4 checkpoint reviewed on the branch.
- **Agents:** feature code by parallel agents in their own worktrees; security code (the
  invocation path, the egress proxy, the builder sandbox, `signing/` changes) by the
  `coder-high` agent type; the lead merges, reviews every merge, and runs all gates
  centrally.
- **Milestone exit gate** (unchanged from P3–P6):
  1. every `make` gate passes locally, judged by its exit code, not its output;
  2. the end-to-end gate test passes at least 40 times with the race detector, and every
     intermittent failure is root-caused;
  3. a dispatched CI run is green in every job;
  4. the milestone's open items are fixed or put to the maintainer;
  5. the hand-off note and the report say what was verified and how.
- **Stops for the maintainer** (AGENTS §7), already known: F0's spec changes and ADRs; every
  new dependency (§4.4 lists them); new CI jobs or gates; the limits' defaults; coverage
  floors of new packages; every change to signing, keys or a security default (C1, the
  function-artifact key).
- **Work log:** `docs/WORKLOG.md` tracks the current milestone. This plan changes only by
  dated decisions recorded in §2.
