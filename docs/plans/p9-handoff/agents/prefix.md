## Shared rules for every P9 feature agent (identical in every brief)

You are a feature agent on Plux (server-driven UI and plugin platform for Flutter; Go server, Dart runtime). The lead reviews and merges your work; quality is judged line by line.

0. **Rule 0:** in your worktree run `git merge --ff-only feat/phase-9` first. If that fails because the worktree was created on a `main` commit and you have no commits of your own, run `git reset --hard feat/phase-9` instead (this happens: agent worktrees start from the default branch). If your task names a wip branch, then run `git merge --no-edit <wip branch>` and resolve conflicts by hand (your migrations get the next free numbers after the highest on `feat/phase-9`; for generated files take either side, then `make gen`). Work only in this worktree and commit there (Conventional Commits, e.g. `feat(auth): …`), every message ending with exactly these two lines:
   `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`
   `Claude-Session: https://claude.ai/code/session_01JKK1NrZX8s8Ewri18tJK82`
   Never push. Never use `--no-verify`; if a hook fails, fix the cause. If your own `git commit` is refused by a permission check, stop and say so in your report; the lead commits for you. Never commit build outputs (build binaries into a temp dir; a stray `backend/cmd/plux/plux` binary has been committed by mistake before).
1. **Scope:** the feature and its tests only. Run only your own tests (`go test ./internal/<pkg>/...`, `go vet` of touched packages, `flutter test <files>`). Do not run lint, coverage, benchmarks or repo-wide gates; do not edit `docs/WORKLOG.md`, changelogs or requirement statuses. You may run `make gen` when you change `proto/`, sqlc queries or registries, and commit its output; never hand-edit generated files (`*.pb.go`, `dbgen/`, `*_gen.go`, `docs/reference/*`).
2. **Reading:** read only the files and plan sections your brief names (plan = `docs/plans/p9.md`); use grep, `sed -n a,bp`, `head`; never dump whole large files or logs; bound every command's output (`| tail -40`).
3. **Code standard** (`docs/engineering/go-standards.md`, binding): SPDX header on every file (copy from a neighbouring file: server packages AGPL-3.0-only; CLI, compiler, schema, bundle, `backend/edition`, `backend/ext` Apache-2.0; `ee/` LicenseRef-Plux-Enterprise); a `doc.go` per new package (responsibility, invariants, spec sections); a doc comment on every exported identifier and function (complete sentences, British English); functions ≤ 80 lines / 50 statements, cognitive complexity ≤ 20, nesting ≤ 5 — split, never annotate; errors wrapped `fmt.Errorf("pkg.Func: %w", err)` at package boundaries, `errors.Is/As`; user-facing failures are plxerr codes (`backend/internal/plxerr`, already registered — use the constants your brief names); `ctx` first for I/O; time and randomness injected; no globals, no `init` side effects; every goroutine has an owner and a shutdown path; gosec-clean; no TODO/FIXME/placeholders/commented-out code; secrets, tokens and keys never logged, returned or stored unhashed/unencrypted.
4. **Architecture:** handlers (`internal/api`) are thin, logic lives in domain packages, storage through sqlc (`internal/storage/queries/*.sql` → `make gen` → `dbgen`); only `internal/signing` touches private keys; outbound HTTP only through the SSRF-safe `internal/httpx` client; limits only from the registry (`schema/limits.json`, read through `internal/schema/limits`), never hard-coded; deny by default; authorisation uses the existing constants in `backend/internal/auth/rbac.go` and `rbac_p9.go` (never add a second const block; a missing permission goes into `backend/internal/auth/permissions.json`, then `make gen`); every state change is audited through `internal/audit` like its neighbours.
5. **Migrations** (`backend/internal/storage/migrations/NNNN_name.sql`) must be contiguous: use the next free number on your base (`ls … | tail -2`); the lead renumbers at merge. Never create placeholder or stub migrations. Expand-only (additive, backward compatible for one release).
6. **Enterprise code (`ee/`)**: `ee/backend` is a separate Go module and cannot import `backend/internal/...`. An ee feature plugs in through a small public extension interface in a public core package `backend/ext/<area>` (standard-library and public types only), a community/no-op default in the core, and a field on `serverapp.Options` (`backend/serverapp/main.go`) that `ee/backend/cmd/plux-server-ee/main.go` sets. Every ee write path is gated with `edition.EnabledForWrite(ctx, edition.Feature…)` and reads with `edition.Readable` (`backend/edition`). The core must build and test without ee (`cd backend && GOWORK=off go build ./...`).
7. **Tests:** hermetic, deterministic, pass with `-race`; cover failure and abuse paths, not only the happy path. Name the requirement: Go `func TestThing_GOV_005(t *testing.T)` with `// Verifies: GOV-005, SEC-103.` in its doc comment; Dart `test('… [SYN-060]', …)`. PostgreSQL integration tests use `storagetest.Open(t)` in `*_integration_test.go` (`PLUX_TEST_DATABASE_URL` is set; the server is running). A `redis-server` binary exists for Valkey-protocol tests.
8. If a document conflicts with the task, or the brief cannot be done as written, stop and report it; do not resolve it yourself.
9. **Final report, at most 8 lines:** branch and commit hashes; what was done; what was not; seams left for other milestones; open questions.

10. **Authorisation matrix:** every new RPC needs an entry in `backend/internal/api/authz_matrix_table_test.go` (`atPerm(auth.X, builder)`, or `public` for unauthenticated RPCs; see neighbouring entries) and every new permission must guard at least one RPC (`TestEveryPermissionGuardsAnRPC`). Your done-check always includes `cd backend && go test ./internal/api/ -run 'Matrix|EveryRPC|EveryPermission|PublicRPCs' -count=1`.

11. **You may be continuing a stopped colleague's work** (your task says so). Trust its design unless it breaks a rule above; do not rewrite working code; finish only what the task lists.
12. **Shared machine:** 4 CPUs, ~20 GB free disk, one PostgreSQL. Run only the packages you touched; never run the whole suite with `-race`; if a build fails with "no space left on device", run `go clean -cache` and retry. `flatc` is at `/root/.cache/plux/flatc-25.9.23/flatc` (put it on `PATH` for `make gen`).
13. **Direct and short-lived:** act on the brief at once; no surveys of the repository, no plans written out, no design alternatives. Do exactly the listed items, commit, run the done-check once, report, and stop. If an item turns out larger than the brief suggests, or you are blocked, commit what works, name the rest in your report and stop; the lead launches a follow-up. Do not wait for, or ask, the lead anything.
