## Your task: P9 E8d — data subject requests and the personal-data map (`SEC-162`)

`SEC-162`: "Administrators MUST be able to export and erase all data associated with a device or pseudonymous user ID (data subject requests) and see where personal data is stored." Plan `docs/plans/p9.md` lines 576–580 (§5.9 Data subjects bullet). Permission `DSRManage` (`rbac_p9.go`); limit `dsr.exportBytes` (`schema/limits.json`); codes `PLX-8501` subject not found (and the 8500 block, `plxerr/registry.go`).

Where device/user personal data lives — find every table with it: `grep -ln "device_id\|user_hash\|subject\|push_token\|ip_prefix\|user_agent" backend/internal/storage/migrations/*.sql` and read only those `CREATE TABLE` blocks (devices and installed releases, device credentials, push tokens (encrypted), telemetry/analytics raw events and their partitions, rollups (aggregates: contributions only via raw events), function logs/invocations, gateway/outbox metadata, notifications inbox (users, not devices), sessions). Audit-log entries are never erased (the hash chain, SEC-140): record the request there instead, and say in the map that audit entries carry only pseudonymous IDs.

Deliver (`backend/internal/dsr`):
1. **Personal-data map:** a declarative registry in Go of each store (table/object prefix), its key column(s) for a device ID and for a pseudonymous user ID, the fields that are personal, retention, and the erase action (delete rows, null fields, or "aggregate only — not erasable, contains no identifier"); a generated `docs/operations/personal-data.md` from it (`make gen` step like other generated docs) with a test that the committed file is current; a completeness test that fails when a migration adds a column named like personal data (`device_id`, `user_id`, `*_hash` of a user, `ip_*`, `user_agent`, `push_token`, `email`, `locale`) to a table the map does not list (`_SEC_162`).
2. **Export:** for a device ID or pseudonymous user ID within an organisation: a JSON archive (one section per store, bounded by `dsr.exportBytes`, streamed to object storage or returned through the API — follow how other large exports are served, grep `objects.Put` in `internal/release`), `PLX-8501` when the subject has nothing anywhere.
3. **Erase:** one transaction per store, in a fixed order, idempotent; leaves only tombstones (subject hash, store, count, time) and an audit entry; telemetry partitions are erased row-wise; push tokens and device credentials revoked so the device must re-register.
4. Migration for requests and tombstones (next free number); `dsr` RPCs in `proto/plux/v1/audit.proto` (additive; it already has the audit export service — add a `DataSubjectService` there or a new `dsr.proto`, your choice, say which); handlers; CLI `plux dsr export|erase|status|map` following `backend/cmd/plux/cmd_governance.go`; matrix entries.
Tests (`_SEC_162`): seed a device and a user across every mapped store, export contains each, erase removes each (query every table afterwards), second erase is a no-op, other subjects untouched, cross-organisation refusal, size bound, map completeness, CLI. Integration tests against PostgreSQL.
Done when: `cd backend && go build ./... && go test -count=1 ./internal/dsr/... ./internal/api/... ./cmd/plux/...` passes.
