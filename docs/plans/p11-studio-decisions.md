# Part A — Decisions

## A1. Rules set by the maintainer

1. **Protect the server.** Every Studio feature that adds server work is bounded: rate limits;
   size and count limits from the limits registry (`LIM-001`); capped history rebuilds; queued
   worker jobs with per-organisation limits; precompressed static assets. A design that moves
   work to the server says how it is bounded.
2. **Legal care.** Every licence question (fonts, ported code, copyleft tools, Apple fonts) gets
   a legal review before its ADR is accepted. Nothing third-party is redistributed unless its
   licence clearly allows it; when in doubt, it is not shipped.
3. **Best performance first**, within the spec's order (security and correctness come first).
4. **Every new dependency** needs an allowlist entry and an ADR first
   ([dependencies.md](../engineering/dependencies.md)). Versions below were checked in the
   session; pin exact versions when adding.
5. **`studio-ui-language.md` is the maintainer's.** Agents draft it only at the maintainer's request and from the
   maintainer's direction; the maintainer accepts it. (Amended 2026-10-22: the accepted version is
   [p11-studio-ui-language.md](p11-studio-ui-language.md), drafted from five mocked-up directions the
   maintainer chose between.)

## A2. Context

- **P11 scope:** 94 requirements tagged P11 (92 `SPEC`, 2 `WITHDRAWN`; 90 `MUST`, 2 `SHOULD`),
  the largest phase. `studio/` today holds only `packages/brand` and `packages/schema`. The
  riskiest part is keeping the canvas layout faithful to Flutter (`STU-005`).
- **Project phase:** P8 at the time of the session (`docs/WORKLOG.md` still said P7; the
  maintainer updates it).
- **Widgets:** the 99 Layer 1 descriptors in `schema/widgets/layer1` are implemented on the
  device; their Studio canvas layout is P11 work. Missing widgets: Part C3.

## A4. Decisions with reasons

### A4.1 React SPA, not Next.js
Studio is a client-heavy editor on a WebGL canvas behind sign-in; server rendering and SEO add
nothing, and `STU-001`/`STU-002` already require a React SPA served by a Bun BFF.

### A4.2 State: Zustand + Immer
- Components re-render only for the slice they select; the vanilla store works outside React.
- **Stores are per area, created in a React provider**, never module-level (`AGENTS.md` §8).
- Immer gives forward and inverse patches: the source of undo and of the JSON Patch autosave.
- The edited document lives in Zustand; TanStack Query holds server-confirmed data.

### A4.3 Canvas renderer: CanvasKit
- **Deciding reason — text layout.** On the device, Flutter lays out text with Skia's
  SkParagraph, also under Impeller (verified in the engine source:
  `lib/ui/text/paragraph_builder.cc` → `txt::ParagraphBuilder::CreateSkiaBuilder`;
  `txt/src/skia/paragraph_builder_skia.cc` → `skia::textlayout::ParagraphBuilder::make`;
  the Impeller flag is only passed through). CanvasKit runs the same code in the browser;
  every other option measures text with the browser and cannot match `STU-005`. Flutter
  itself removed its browser-text HTML renderer in 3.29.
- Painting follows Skia's model (rounded rects, blur shadows, gradients, clips, layers, blend
  modes). The device paints with Impeller, so pixels differ slightly; conformance compares
  positions and sizes, not pixels.
- **Build our own CanvasKit from the Skia revision Flutter 3.47.5 pins**, trimmed (no Skottie,
  PDF or extras), as `plux-svgc` already builds Skia path ops (ADR-0027).
- *Measured:* npm `canvaskit-wasm` 0.42.0 default 2.80 MiB gzip, full 3.14 MiB; PixiJS 8.22.0
  231 KiB. `STU-122`'s 1.5 MiB covers initial JavaScript only; the canvas loads on demand, is
  prefetched while the apps grid is open, compiled with `compileStreaming`, cached immutable.
- Why not PixiJS: sprite/game engine, text through browser Canvas2D, no faithful blur shadows,
  duplicate scene graph. Why not raw WebGL2: we would rebuild Skia (paths, AA, shadows, clips,
  glyph atlases, HarfBuzz, ICU, bidi). Canvas2D (Konva, Fabric), SVG/DOM: too slow at scale,
  browser text, breaks `STU-003`. Vello: needs WebGPU, young. ThorVG: no Flutter text layout.
- Costs: size; manual `.delete()` (one ownership wrapper plus a leak check in tests); a parallel
  accessible DOM tree (true for any WebGL option).

### A4.4 Layout engine: custom port of Flutter's layout code
- Yoga and Taffy implement CSS layout; Flutter passes min/max constraints down and sizes up.
  `RenderFlex` (read in source): inflexible children laid out unbounded on the main axis;
  flexible children split only leftover space by flex factor (tight/loose fit); no flex-shrink;
  overflow keeps sizes; own `MainAxisSize.min` and baseline rules. Yoga's flex-shrink defaults
  to 0, unlike browsers. Each difference fails `STU-005`.
- CSS engines cover only Row/Column/Flex/Stack/Wrap/Padding/Align/SizedBox of the 99 Layer 1
  widgets. Slivers (CustomScrollView, SliverList/Grid/AppBar/FillRemaining, ListView, GridView,
  PageView), LimitedBox (applies only under unbounded constraints), FittedBox, AspectRatio,
  FractionallySizedBox, Baseline and Material/Cupertino composites (Scaffold's multi-child
  layout, AppBar's toolbar, ListTile's render object, button tap-target sizes) need custom code
  anyway — two models plus glue.
- Incremental relayout (relayout boundaries) comes with the port (`STU-121`).
- *Measured:* `yoga-layout` 3.2.1, last release December 2024, 49 KiB gzip; Taffy has no
  official JS binding (third-party `taffy-layout` 3.0.0, 207 KiB); the relevant Flutter
  rendering files total about 24,000 lines including docs, debug checks and painting.
- **How:** port box constraints and sizes, intrinsic dimensions, baselines and the sliver
  protocol, and each render object, from the pinned Flutter source into
  `studio/packages/layout`, recording the source revision per file (an upgrade is a diff).
  Text through SkParagraph with Flutter's rules (text scaler, strut, text height behaviour,
  max lines, ellipsis). This is the largest single piece of Studio.
- **Conformance suite:** headless `flutter_test` writes every node's global rect to golden JSON
  per widget × device frame × locale × text scale; the TypeScript engine is compared in CI
  within the tolerance; a Flutter upgrade regenerates goldens and the diffs are ported.
- **Licence:** ported code keeps Flutter's BSD-3-Clause notice, annotated in `REUSE.toml`
  inside AGPL `studio/` (compatible; legal review per A1.2).
- Layout may later run in the canvas worker — decided in A5.1 (it does).

### A4.5 Action graph editor: React Flow + dagre
- A full-screen DOM overlay (`STU-063`), separate from Plux Canvas; nodes are small forms that
  need real DOM (input methods, focus, screen readers, `STU-011`).
- Graphs are small and bounded (spec §9.4: `next`, `onSuccess`, `onError`, named branches);
  57 action types in `schema/actions`.
- React Flow gives pan/zoom, selection, marquee, connection dragging with `isValidConnection`,
  edge paths, minimap, controls, keyboard access (Tab, Enter/Escape, arrows) and localisable
  `ariaLabelConfig` (`STU-012`). *Measured:* about 52 KiB + 36 KiB (`@xyflow/system`) gzip
  unminified, plus d3 dependencies. It pins Zustand ^4, so a second copy ships beside Zustand 5
  (a few KiB; note in the ADR).
- Node types generated from `schema/actions/*.json`: `branches` → named output handles;
  `onSuccess`/`onError` fixed outputs; `inputs` with types → node form.
- Path validation uses the compiler's rules via the WebAssembly validator (A4.7), never a TS copy.
- dagre (pure layout, about 21 KiB gzip with graphlib) also drives app-canvas auto-layout
  (`STU-032`) and screen auto-layout (`STU-050`).
- Rejected: custom editor (months of generic work); Rete.js 2 (last release June 2025);
  LiteGraph (canvas-drawn widgets, poor accessibility); ELK (licence; reserve).

### A4.6 Inline PXL editor: CodeMirror 6
- *Measured:* about 119 KiB gzip with autocompletion and lint, against about 685 KiB gzip for
  Monaco's core; cheap per instance (dozens per screen); styles like an input with shadcn;
  works with screen readers and touch.
- Monaco stays for the full-screen JSON and Rust editors (`STU-001`). Both use the same PXL
  language service (`PXL-008`): completion, hover types, inline errors, signature help.

### A4.7 Compiler validation in the browser
- The real Go validator (`compiler.NewValidator`, `ValidatePage`) compiled to WebAssembly, in a
  Web Worker, one module shared with the PXL language service. The server validates again on
  save and publish and stays the authority.
- *Measured:* builds unchanged with `GOOS=js GOARCH=wasm`; 11.8 MiB raw, 3.1 MiB gzip; loaded
  only when an editor opens; cached.
- `ValidatePage` checks only the edited page and its graphs — validation as you type (`STU-064`).
- Optimal for correctness (one validator, Studio and server never disagree), the usual pattern
  (language tools in WebAssembly in a worker). Not the fastest possible: large, slower start,
  `syscall/js` bridge costs. Speed-ups if the prototype needs them: one batched message per
  edit; split validation from bundle encoding; try TinyGo; only then move project-wide checks
  to the server, keeping per-keystroke checks local.
- Rejected: TypeScript reimplementation (drift); server round-trips only (latency, offline).

### A4.8 Styling: Tailwind CSS v4
- Required by `STU-001`; shadcn is written in it.
- Tokens from `@plux/brand` generate the `@theme` CSS variables; Tailwind's default values are
  reset so only token-backed utilities exist; the same token source feeds CanvasKit.
- The token set defines the scale names shadcn components use (spacing, sizes, radius, colours);
  each shadcn component is adapted to token-backed utilities when it is added, so no component
  relies on a reset default.
- Themes (light, dark, system) and density switch by variables, no re-render
  (`STU-010`, `STU-014`). Logical utilities and the `rtl:` variant for RTL (`STU-012`).
- One static stylesheet, no runtime style injection: CSP needs no style exceptions
  (`STU-002`); utility CSS stops growing with the app (`STU-122`). No runtime CSS-in-JS.

### A4.9 Routing: TanStack Router
- Typed routes, params and `<Link>`; **schema-validated typed search params**: the URL holds
  location only — app, plugin, screen, selection anchor, viewport, open overlay and drawer. Preview
  switches (device frame, locale, theme, text scale) live in the user's profile (functional
  decisions F10). Full route map: [p11-studio-routing.md](p11-studio-routing.md).
- Loaders prefetch Query caches (preload on hover/intent); lazy route files (`STU-122`);
  overlays are search-param or nested routes inside the canvas route, so the canvas never
  unmounts (`STU-063`).
- React Router 8 gets full type safety mainly in its framework mode (code generation, server
  setup) that we do not use.

### A4.10 Server data: TanStack Query + Connect Query
- Connect Query generates typed hooks and query keys per RPC from protobuf (`STU-001`).
- Optimistic mutations with rollback; ordered debounced JSON Patch autosave (`STU-004`).
- Keys include the document revision; a new revision is a new key (ADR-0015).
- Router loaders prefetch; devtools, paused mutations, structural sharing built in.
- The editor's working copy stays in Zustand with undo; keystroke changes never go through the
  Query cache.
- Live device streams (`STU-066`) bypass Query: Connect client → Zustand.

### A4.11 Forms: TanStack Form + Zod 4
For ordinary forms (new-app wizard, publish flow, admin, policies, settings): fully typed,
field-level re-renders, async validation, Zod via Standard Schema; shadcn has an integration.
Zod is configured with `z.config({ jitless: true })`: otherwise it probes `new Function`, which
the strict CSP (Part B §11.2) forbids.
React Hook Form 7.90 is the fallback (weaker types for nested/dynamic forms). The Properties
panel uses no form library: descriptor-generated editors write JSON Patch into the store and
are validated by the WebAssembly validator.

### A4.13 i18n: Lingui 6
- ICU MessageFormat (the standard Plux apps use, `I18N-001`); catalogues compiled at build time
  (few-KiB runtime, no parsing in the browser, CSP-friendly); typed message IDs.
- **Explicit keys** in `<feature>.messages.ts` with English text and translator description;
  strict extraction fails on missing and unused keys.
- Locales `en`, `de`, `ar`; dates, numbers, plurals, RTL via `Intl` (CLDR).
- Rejected: react-i18next (non-ICU default format); FormatJS (heavier runtime).

### A4.14 UI components: shadcn/ui on Base UI
- shadcn is a generator: the code is ours, styled with our tokens; no outside design language
  to fight (`STU-010`, Appendix J).
- Base UI: shadcn's default since July 2026; actively released; built by former Radix, Material
  UI and Floating UI authors; focus management, keyboard navigation, direction provider.
- **Maintainer chose Option A:** change `STU-001` to "shadcn/ui on Base UI primitives". Radix
  is not deprecated (radix-ui 1.8.1, October 2026) but is not shadcn's direction. React Aria
  Components has the strongest accessibility but shadcn does not build on it.
- Alongside: **command palette** (`STU-013`) built on Base UI Dialog + Autocomplete, fed by the
  command registry — not cmdk, which depends on four Radix packages and would bring Radix back
  beside Base UI; **sonner** (toasts); **Phosphor Icons** (A4.20); **TanStack Table + Virtual**
  (localisation grid, audit log, device lists).
- Base UI's `CSPProvider` passes the request's nonce to the styles Base UI injects (Part B §11.2).

### A4.15 BFF: Hono, stateless
Hono ships CSRF, secure headers with per-request CSP nonces, cookies, body limit and timeout
middleware (checked in the package), has no runtime dependencies, uses standard
`Request`/`Response`, runs natively on Bun. The BFF mostly proxies Connect calls typed by
protobuf, so Elysia's Eden types and speed add little and tie us to Bun.
- **Sessions (decided later, functional decisions F19):** the BFF keeps no session state. The
  server already issues the browser session (`__Host-plux_session`, stored hashed in PostgreSQL)
  and CSRF tokens (ADR-0026); the BFF serves the sign-in pages, proxies `/auth/*` and passes the
  session cookie through. The server performs sign-in, including OIDC/SAML from P9 (`GOV-004`).
  `oauth4webapi` was first chosen for a BFF-side OIDC flow and is **dropped**. `STU-002`'s
  wording changes accordingly (C3).

### A4.16 Build: Vite 8 on the Bun runtime
- Official Vite plugins for every chosen library: Lingui (needs one for its compile-time
  macros), TanStack Router (route generation, code splitting), Tailwind v4, WebAssembly.
  `bun-plugin-tailwind` 0.1.2 is a year old; there is no Lingui Bun plugin.
- Fine-grained code-splitting control (`STU-122`); mature dev server with React Fast Refresh.
- **Maintainer chose Option A:** `STU-001` "built and served with Bun" reads as Vite on the Bun
  runtime, served by the Bun/Hono BFF; make the wording explicit.

### A4.17 Monorepo layout

studio/apps/bff           Hono BFF (stateless): sign-in pages, session pass-through, CSP nonces, API and stream proxy

### A4.18 Lint and format
Biome only, as today (`biome ci` in `make studio-check`). No ESLint, Prettier or Oxlint.

### A4.19 Drag and drop
- Inside the canvas (widgets, plugin boxes, links): Plux Canvas's own pointer handling.
- Insert panel → canvas, file and asset drops, list reordering in panels: **Pragmatic drag and
  drop** (tiny, native DnD, DOM → canvas element with our own hit-testing, files dragged in from the computer).
- Layers tree (`STU-061`): **Headless Tree** (tree semantics, keyboard moves, virtualisation).
- Every drag has a keyboard alternative ("Move to…", nudging) — WCAG 2.2 (`STU-011`, `STU-067`).
- Not dnd-kit: classic 6.3.1 unreleased since December 2024; the rewrite is 0.5.1.

### A4.20 Virtualisation, charts, icons, animation
- **TanStack Virtual:** headless; rows, columns and 2D grids (localisation keys × locales,
  `STU-091`); measured row heights (logs, audit); pairs with TanStack Table and Headless Tree.
  Rejected: react-window 2 (weaker for variable grids), react-virtuoso (opinionated), virtua
  (pre-1.0).
- **Recharts 3** via shadcn Chart for Analytics, Releases, Experiments, Functions: CSS-variable
  tokens, built-in accessibility layer, lazy-loaded. **uPlot 1.6** (canvas, tiny; last release
  March 2025, stable) for the live device performance stream (`STU-066`). Rejected: ECharts 6
  (heavy, separate theming), visx (too low-level).
- **Phosphor Icons, duotone weight**, for Studio's own UI (maintainer, 2026-10-22; UI language U8),
  replacing Lucide: Lucide is shadcn's default and the most recognisable mark of a generated
  interface; Phosphor's duotone outline-with-fill suits the rounded design and gives Studio its own
  character. MIT. *Checked:* `@phosphor-icons/core` 2.1.1 (SVG assets, last published March 2024)
  and `@phosphor-icons/react` 2.1.10 (May 2025). The set is stable rather than active, so Studio
  inlines the pinned SVG paths through one `Icon` component and depends on no runtime package; a
  missing icon is drawn in the set's grid and style and recorded in the catalogue. The apps' icons
  stay the Material Symbols and Cupertino sets the server embeds. Phosphor has no RTL-mirror
  metadata: the catalogue keeps a `mirrors` list.
- **No animation library:** the required animations (bundle expansion 150–200 ms, `STU-044`;
  ghost-screen pulse about 2 s, `STU-053`) run in Plux Canvas; panels and dialogs use CSS
  transitions with duration/easing tokens and Base UI state attributes; reduced motion honoured.

### A4.21 Diff tooling
- Patches while editing: Immer → RFC 6902.
- Applying and diffing: `rfc6902` (`fast-json-patch` unreleased since 2022).
- Text diff: Monaco's diff editor over the server's canonical JSON (JSON editor vs last
  published, `STU-064`; history compare, `STU-069`).
- "What changed" lists (publish flow, history): our own diff keyed by entity UUIDv7
  (`SCH-002`) — correct moves, renames and adds without guessing array order (unlike
  `jsondiffpatch`).
- All diffing in the browser; the server only serves the two snapshots.

### A4.22 Component catalogue tooling
No Storybook or Ladle (a second large toolchain). A **development-only catalogue page** in the
same Vite app renders each shared component's states from `*.cases.tsx` files beside it
(loading, empty, error, long text). Playwright opens it in `en`, `en-XA`, `ar-XB` for
overflow, keyboard and accessibility. `CATALOGUE.md` stays the written reference agents read
first.

## A5. Architecture decisions

### A5.1 Threading: Plux Canvas in one dedicated Web Worker
- The worker owns layout, CanvasKit, the scene graph, hit-testing and raster snapshot caches,
  and presents frames directly via `transferControlToOffscreen()` (no per-frame copy; Flutter's
  multi-threaded skwasm copies via `transferToImageBitmap`, reported slow in Firefox/Safari).
- The main thread keeps React, the Zustand document and undo, input capture and the accessible
  DOM tree. React work can never drop a canvas frame (`STU-120`, `STU-045`); edits reach the
  worker in well under a millisecond (`STU-121`).
- One worker, not two: layout needs SkParagraph, so splitting would load CanvasKit and fonts
  twice and add a hop.

| Flow | Path |
|---|---|
| Edits | edit pipeline → JSON Patch → autosave, undo, validator worker, canvas worker (one stream) |
| Input | pointer/wheel captured on main, coalesced per frame, posted; pan, zoom and drag run in the worker; a finished drag sends one patch back |
| Back channel | at most once per frame: selection, hover, bounds of changed nodes, layout diagnostics → panels, accessible tree (Part B §9.5), scene queries for tests (§9.2, async snapshot) |
| Text editing on canvas | DOM editor positioned from worker-supplied bounds |
| Drops from panels | main posts the drop point; the worker hit-tests and returns the target |
| Fonts, images | bytes transferred without copying |
| Overlays (`STU-063`) | "pause" stops drawing; canvas element stays mounted; state lives in the worker |
| Context loss | the worker rebuilds GPU resources from the scene model (Part B §9.6) |

- No SharedArrayBuffer at first (needs cross-origin isolation headers); later only if the back
  channel measures as a bottleneck.
- The canvas module talks only through its message interface: the same code runs on the main
  thread as a fallback for browsers that fail; `bun test` drives it directly; Playwright drives
  the real worker.
- *Verified in headless Chromium:* `requestAnimationFrame` in a worker, WebGL2 on
  OffscreenCanvas, CanvasKit surface from the transferred canvas, 120 frames of 1,000 rounded
  rects. **Not verified:** Firefox, Safari, real GPU frame rates (prototype, C4).

### A5.2 Live channels: Connect server streaming, no WebSocket
- Follows today's code: `WatchPublish` already server-streams (`proto/plux/v1/publish.proto`);
  the server speaks HTTP/1.1 and h2c (`backend/internal/server/server.go`); locks are unary
  leases (`AcquireLock`, `RenewLock`, `GetLock` in `plugin.proto`); the only WebSocket code is
  the device data-source gateway.
- Server → browser: server streams, typed by protobuf, same clients, same BFF auth and CSRF
  path. Browser → server commands (send to device, edit device state, mocks, inspect
  selection): unary RPCs, within `DEV-010`'s 500 ms. A WebSocket would add a second, untyped
  protocol with its own upgrade, origin checks and auth.
- Per tab: **one events stream** (notifications, lock changes, publish progress) and **one
  stream per paired device**; HTTP/2 between browser and BFF (browsers allow six HTTP/1.1
  connections per origin); each stream resumes from a cursor with bounded server buffering
  (`DEV-021`).
- The BFF (Hono) proxies streams unbuffered, passes the user's session cookie through, sends heartbeats, sets
  deadlines.
- Consequences:
  - Live lock and notification events need a server fan-out (e.g. PostgreSQL
    `LISTEN`/`NOTIFY`); `WatchPublish` polls today (`backend/internal/api/release.go`). P11
    backend work.
  - **Connect-Web in browsers supports only unary and server streaming**, so the
    client-streaming `UploadAsset`, `ImportDraft` and `UploadSource` cannot be called from
    Studio: unary chunked variants or a BFF upload endpoint (`proto/` change, C2).
  - The device half is P10 (`DEV-020`, not built); design the device stream's messages with it.

### A5.3 Rust editor bridge (`FN-033`)
- LSP JSON-RPC over Connect: one server stream per editor session (`LanguageServer.Open`:
  diagnostics, progress, responses) and batched, sequence-numbered unary `Send` calls (ordered
  edits; HTTP/2 multiplexing keeps keystroke latency low).
- Browser: `monaco-languageclient` with a small custom transport; Monaco speaks standard LSP.
- **Security first:** rust-analyzer runs build scripts and procedural macros (arbitrary user
  code). It runs inside the function build sandbox (`builder` isolation of ADR-0064, `L-4`: no
  credentials) with build scripts and proc macros off, no network, CPU/memory/time limits, one
  sandbox per session.

### A5.4 Fonts
- **Studio UI** (maintainer, 2026-10-22; UI language U7): Instrument Sans for controls and text,
  Instrument Serif for names and titles, DM Mono for numbers, identifiers and code (all OFL-1.1,
  self-hosted per Part B §11.5). They cover Latin scripts only: the Arabic pairing (proposed Noto
  Sans Arabic and Noto Naskh Arabic) and later scripts (e.g. Ethiopic) are an open maintainer
  decision. The earlier choice, Noto Sans with Noto Sans Arabic, is replaced.
  Sora SemiBold for the wordmark only (Appendix J).
- **Canvas, app fonts:** the canvas worker fetches the same verified font assets the device
  loads (ADR-0032 § Fonts per script) and receives their bytes without copying.
- **Canvas, platform defaults:** Studio ships open-licensed ones: Roboto for Material, Noto
  fallbacks per script.
- **Fonts bundled in host apps** (used by name on the device, invisible to Studio today):
  proposed — `plux native scan` / `native sync` upload them with the native catalogue
  (additive; maintainer approval, C2).
- **SF Pro — never served or stored by Plux.** Apple's licence forbids embedding and
  redistribution and allows only UI mock-ups for Apple platforms by registered developers; Apple
  points web use to `system-ui`.
  - Chromium: the user's own installed SF Pro via the Local Font Access API (`queryLocalFonts`,
    Chrome/Edge 103+, with permission); bytes stay in the browser.
  - Firefox, Safari (no Local Font Access) or no SF Pro installed: a substitute plus the
    "device preview is authoritative" notice (`STU-006`).
  - Android device frames with Cupertino style: always the substitute (the licence forbids
    mock-ups for non-Apple systems).
  - **Counsel confirms before the ADR is accepted.**

### A5.5 Undo persistence (`STU-069`)
- Server-side, on the snapshots already stored for every accepted write (`SRV-031`, done; kept
  under the server's at-rest encryption rules). Nothing in IndexedDB: sensitive fields on
  disk, breaks across tabs and devices, diverges after a lock takeover (`SRV-041`).
- The browser holds the in-memory stack; after a reload it rebuilds from this editing session's
  snapshots. Undo applies the inverse patch as a **new forward write** (ADR-0015 linear history).
- Proposed API addition: tag each write with an editor-session ID and store its inverse patch
  (`proto/` change, C2).
- Edits inside the 500 ms autosave delay flush on tab hide through the generated Connect client
  with a `keepalive` fetch transport, via the BFF (no hand-written fetch, Part B §2.2).
- Server protection: inverse patches are a few hundred bytes; rebuilds capped to the session's
  recent entries; writes rate-limited.

### A5.6 Thumbnails, screenshots, visual diff
- App-card (`STU-021`) and ghost-screen (`STU-052`) thumbnails: rendered **in the browser** from
  the canvas's cached CanvasKit snapshots, uploaded only when changed (small, content-addressed,
  rate-limited).
- Publish visual diff (`STU-100`): **server-side**, as the spec requires ("rendered server-side
  on standard devices"), as a bounded, queued worker job with per-organisation limits from the
  registry.

### A5.7 Studio's own telemetry (minimal)
- Required: `OBS-001` (W3C Trace Context from Studio). The BFF starts it on every proxied call;
  no browser SDK.
- Worth having: uncaught browser, canvas-worker and worker errors, and real-user timings (LCP,
  long frames via `web-vitals`) to show `STU-120`–`STU-123` hold in the field. One BFF endpoint
  → the server's structured logs (`OBS-003` redaction).
- Guards: no document content, personal data or sensitive fields; sampled and rate-limited at
  the BFF; an administrator switch turns it off; no third-party services (Part B §11.5).

### A5.8 Browsers, reference laptop, performance CI
- **Reference laptop** is defined in spec §30.1: 4-year-old mid-range laptop, integrated GPU,
  Chromium-based browser. No GPU purchase. `STU-120` is confirmed by hand on it before each
  release; results in `docs/benchmarks/`.
- **CI** (hosted runners, no GPU): headless Chromium with software rendering, tracking
  GPU-independent costs (layout time, draw-call count, CPU time per frame), failing on >10%
  regression against its own baseline (`QA-007`), not on absolute 60 fps.
- **Browsers:** full support for the current and previous majors of Chrome and Edge; supported
  for the current and previous Firefox (plus ESR) and Safari, using the main-thread canvas
  fallback where worker WebGL is missing; no WebGL2 → a clear "unsupported browser" message.

### A5.9 Versions, deployment, caching
- Studio web app and BFF ship in **one image, released with the server at the same version**.
  The API stays additive (`buf breaking`, `SRV-000`): an older Studio works against a newer
  server; Studio refuses a server older than it expects. The BFF reports versions; open tabs
  show "Studio was updated, reload" after autosave flushes.
- One container started alongside the server roles (`DEP-002`; the Compose stack already plans
  Studio); serves static files and the BFF; no CDN, nothing third-party (air-gapped installs).
- Hashed assets (incl. CanvasKit and validator WebAssembly): one year, `immutable`, **Brotli
  precompressed at build** (no per-request compression CPU). `index.html`: `no-cache` (fresh CSP
  nonce). API responses never browser-cached (Query caches). **No service worker** for now
  (stale-version risk, Studio needs the network anyway).

### A5.10 Generated clients
- Add local `protoc-gen-es` (from `@bufbuild/protoc-gen-es`, pinned in `studio/bun.lock`, run
  from `studio/node_modules/.bin`) to `proto/buf.gen.yaml` beside the Go and OpenAPI plugins;
  no network, no remote plugin (`CI-003`). Connect-ES v2 needs only this plugin (messages and
  service descriptors); Connect Query uses the descriptors.
- Output `studio/packages/api/src/gen/*_pb.ts`, committed, marked generated; exclude
  `plux.internal.pkcs11.v1` and `plux.internal.fn.v1` with `exclude_types` (`SEC-120`).
- `make gen` runs `bun install --frozen-lockfile` before buf; the folder joins `go-gen-check`'s
  paths; SPDX headers and a `REUSE.toml` Apache-2.0 annotation.

# Studio Development

How Plux Studio (`studio/`) is built: structure, design system, localisation and direction, state, canvas, testing, performance, security, and the rules that keep agents' context and token use small. It is binding for every contributor, human or agent. The specification says *what* Studio does (spec §21, `STU-001`–`STU-123`); [typescript-standards.md](../engineering/typescript-standards.md) says how TypeScript is written; this document says how Studio is put together.

The stack is fixed by `STU-001` (with the wording changes of ADR-0014): Bun as runtime, package manager, test runner and BFF server; Vite on the Bun runtime as the build tool; strict TypeScript; React; TanStack Router, Query and Form; shadcn/ui on Base UI; Tailwind CSS v4; Monaco for full-screen editors and CodeMirror 6 for inline PXL fields; Connect-ES; Plux Canvas on CanvasKit. A package is installed only once it is on the [allowlist](../engineering/dependencies.md).

Rules are numbered so a review can cite them ("studio-development §6.3"). A rule that no longer serves the project is changed here in a pull request, never ignored.

---

## 1. Principles

1. **The device is the truth; Studio is the instrument.** The canvas previews; the conformance-tested layout engine (`STU-005`) and the paired device decide.
2. **Every claim has a test or a measurement.** A UI that "looks right" is not evidence. Behaviour is proven by assertions on the DOM, the scene model or numbers; performance by benchmarks against `STU-120`–`STU-123`.
3. **One source per fact.** Tokens come from `@plux/brand`, strings from the message catalogue, commands from the command registry, contracts from `@plux/schema` and the generated Connect-ES clients. Nothing is copied.
4. **Direction- and language-agnostic by construction.** Every screen works in left-to-right and right-to-left and in any Studio locale from its first commit. Retrofitting is not allowed.
5. **Small, named, findable.** A feature is a folder with a known shape and a short README, so a reader — or an agent — finds the right file without exploring.
6. **Cheap to verify.** The test is the cheapest way to see a change working. Screenshots are the most expensive and are not used by agents without approval (§13).
7. **Protect the server.** Work that reaches the server is bounded: rate limits, registry limits (`LIM-001`), capped rebuilds, queued jobs. A feature that adds server work states how it is bounded.

## 2. Architecture

Studio lives entirely under `studio/`: its apps in `studio/apps/` and its TypeScript packages in `studio/packages/`. The root `packages/` holds the Dart and Flutter packages and is never used for Studio code.

| Path | Owns | May import |
|---|---|---|
| `studio/apps/web/` | The React single-page application: shell, routes, areas, panels, overlays, the development-only catalogue page | every `packages/*` |
| `studio/apps/bff/` | The stateless Hono backend-for-frontend on Bun: sign-in pages, pass-through of the server's session cookie and CSRF token, CSP nonces, API and stream proxy, rate limits, version reporting, the error/metrics endpoint (`STU-002`, `SEC-101`) | `packages/schema`, `packages/api`, `packages/i18n` (server-side locale negotiation) |
| `studio/packages/canvas/` | Plux Canvas: CanvasKit scene graph in the canvas worker, hit-testing, arrows, raster caches, the message interface (`STU-003`, §21.5) | `packages/layout`, `packages/brand`, `packages/schema` |
| `studio/packages/layout/` | The layout engine ported from Flutter, text through SkParagraph (`STU-005`, `STU-006`); no DOM | `packages/brand`, `packages/schema` |
| `studio/packages/validator/` | The Go validator compiled to WebAssembly and the PXL language service, run in a worker (`PXL-008`, `STU-064`) | nothing in `studio/` |
| `studio/packages/api/` | Generated Connect-ES clients (`*_pb.ts`) | nothing in `studio/` |
| `studio/packages/ui/` | Shared components on shadcn/ui and Base UI, the component catalogue and `*.cases.tsx` (§5) | `packages/brand`, `packages/i18n` |
| `studio/packages/i18n/` | Studio's own message catalogues, locale negotiation, direction, formatting (§7) | nothing in `studio/` |
| `studio/packages/brand/` | Brand tokens (spec Appendix J) and contrast utilities | nothing in `studio/` |
| `studio/packages/schema/` | Generated contracts: document types, limits, registries (`*.gen.ts`) | nothing in `studio/` |

2.1. **Imports flow downwards only.** `studio/packages/*` never import from `studio/apps/*`; `studio/packages/canvas` and `studio/packages/layout` never import React or `studio/packages/ui`. A policy check enforces the table with the first P11 package.

2.2. **Studio never reaches the database or object storage** (layering rule L-7). Every call goes browser → BFF → API through the generated Connect-ES clients; no hand-written `fetch` to the API. Loading Studio's own static files (WebAssembly, fonts, catalogues) from the installation is not an API call.

2.3. **The browser never holds a token** (`SEC-101`): no OAuth token, API token or secret in JavaScript, `localStorage`, `sessionStorage`, IndexedDB or URLs.

2.4. **Spec map.** Each area of spec §21 has exactly one home:

| Spec | Area | Home in `studio/apps/web/src/areas/` |
|---|---|---|
| §21.2 | Shell, command palette, profile settings | `shell/` |
| §21.3 | Apps grid | `apps-grid/` |
| §21.4–§21.5 | App canvas, bundled arrows | `app-canvas/` (scene in `packages/canvas`) |
| §21.6 | Plugin canvas | `plugin-canvas/` |
| §21.7 | Screen editor, panels, overlays, bottom drawer | `screen-editor/` |
| §21.8 | Safety rules | `safety/` (used by the areas above) |
| §21.9 | Components and templates | `library/` |
| §21.10 | Releases, approvals, experiments | `releases/`, `approvals/`, `experiments/` |
| §21.11 | Functions, localisation, design system, data, analytics, devices, admin | one folder each, named after the area |

2.5. **Threads.** The main thread runs React, the document store and undo, input capture and the accessible DOM tree. Plux Canvas (layout, CanvasKit, scene, hit-testing, caches) runs in one dedicated worker drawing through `transferControlToOffscreen()`. The validator and the PXL language service run in their own worker. Workers talk through typed message interfaces only; the canvas code also runs on the main thread as the fallback for browsers without worker WebGL.

2.6. **Live data.** Server → browser data (notifications, lock changes, publish progress, device streams) uses Connect server streaming through the BFF: one events stream per tab, one stream per paired device, HTTP/2, resumable from a cursor. Browser → server commands are unary RPCs. No WebSocket.

## 3. Feature folders

3.1. **One folder per feature, one shape.**

```
areas/<area>/<feature>/
  README.md            purpose, requirement IDs, public API, files — at most 40 lines
  index.ts             the only export point
  <Feature>.tsx        the root component, with its private sub-components
  <part>.tsx           a sub-component, once it is reused or its own unit
  use<Thing>.ts        hooks: data, commands, derived state
  <feature>.messages.ts  message descriptors for this feature (§7.4)
  <feature>.test.tsx   component tests (§12)
  model.ts             pure logic, no React, no I/O
  model.test.ts
```

3.2. **The README is the map.** It lists the requirement IDs the feature implements, what it exports, and one line per file. It is updated in the same change as the code; a stale README is a bug.

3.3. **Size guidelines.** These are recommendations, not gates. Code that belongs together may stay in one file; split when a part is reused, tested on its own, or the file becomes hard to navigate. A reviewer may ask for a split beyond these sizes, and the author says why the code stays together.

| Item | Recommended size |
|---|---|
| Source file (not tests, not `*.gen.ts`) | about 300 lines |
| Component function | about 120 lines, including JSX |
| Other functions | about 60 lines |
| Props of a component | about 8; more often means the component does two jobs or needs a grouped prop |
| JSX nesting inside one component | about 6 levels |

The one enforced limit is Biome's `noExcessiveCognitiveComplexity`, already an error in `studio/biome.json`.

3.4. **Names.** Components `PascalCase.tsx`; hooks `useCamelCase.ts`; pure modules `kebab-case.ts`; tests next to the file with `.test.ts(x)`; catalogue cases `<Component>.cases.tsx`. Names say what a thing is in the product's vocabulary (spec §35 glossary): `BundledArrow`, not `CurvyLine2`.

3.5. **No barrel chains.** Only a feature's or package's `index.ts` re-exports, and only its public API.

## 4. Design system

4.1. **Three token layers.** Brand tokens (`@plux/brand`, spec Appendix J) → semantic tokens (`surface.canvas`, `text.primary`, `accent.selection`, `status.warning`, `radius.panel`, `elevation.overlay`) → component tokens where a component needs its own. Components use semantic or component tokens, never brand tokens directly, so a theme or a brand overlay changes one layer. The same token source feeds Tailwind and Plux Canvas.

4.2. **No raw values.** No hex, `rgb()`, `hsl()`, pixel, `rem` or shadow literals in components, and no Tailwind arbitrary values (`bg-[#…]`, `p-[13px]`, `rounded-[…]`). The Tailwind v4 `@theme` is generated from the tokens and Tailwind's default values are reset, so only token-backed utilities exist. A lint rule enforces this with the first component. No runtime CSS-in-JS.

4.3. **The visual language is Porcelain** ([studio-ui-language.md](p11-studio-ui-language.md), accepted by the maintainer 2026-10-22, with the reference page [studio-ui-reference.html](p11-studio-reference.html)): a cool, whitish workspace with a dark theme and a system setting; generous radii and pills; three floating glass capsules, floating panels and a floating drawer over the canvas; Electric Violet only for selection, focus and the primary action; colour only for meaning (selection, status, arrows); dense, information-rich presentation through a fixed set of patterns (status pills, metric strips, meters, sparklines). Studio follows `STU-010`, `STU-060`–`STU-062` and Figure 21-2 as written. A new colour use states its meaning in the token's name; a new pattern is added to the UI language and the reference page before it is built.

4.4. **Themes and density** (`STU-014`): light, dark and system; compact density by default and comfortable as the option, both as token sets (CSS variables), not conditional class names. A high-contrast theme exists for the canvas preview (`STU-112`) and is offered for the shell.

4.5. **Contrast is computed, not eyeballed.** Every text/background and UI-component token pair is checked with the `@plux/brand` contrast utilities in both themes: 4.5:1 for text, 3:1 for large text and components (`STU-011`). The check is a unit test over the token tables.

4.6. **Typography.** The wordmark uses Sora SemiBold (Appendix J). Instrument Serif names things (screens, panels, sections, plugins), Instrument Sans carries controls and sentences, DM Mono carries every number with a unit, identifier, path and code (OFL-1.1, self-hosted; UI language U7). Arabic uses the pairing the maintainer decides (UI language U7).

4.7. **Motion** comes from duration and easing tokens (arrow expansion 150–200 ms, `STU-044`). No animation library: canvas animations run in Plux Canvas; panels and dialogs use CSS transitions and Base UI state attributes. Every animation honours `prefers-reduced-motion` by reducing to an instant change.

## 5. Components

5.1. **Reuse before writing.** Before creating a component, search the catalogue (§5.2). A second component that does the job of an existing one is rejected in review.

5.2. **The catalogue.** `studio/packages/ui/CATALOGUE.md` lists every shared component: name, one-line purpose, props, variants, keyboard behaviour, whether its icons mirror in RTL, and when *not* to use it. Each shared component has a `<Component>.cases.tsx` with its states (loading, empty, error, long text), rendered by the development-only catalogue page. A new or changed shared component updates its entry and its cases in the same change; a policy check compares the entries with the package's exports.

5.3. **Components render; they do not decide.** Business rules — safety rules (§21.8), validation, permissions, link derivation — live in `model.ts` or hooks and are unit-tested without React. A component that contains an `if` on product rules is split.

5.4. **Every state is designed.** Each data-driven component handles loading, empty, error and success, and long text, in every Studio locale. The four states map to the canvas mock states of `STU-058`, so the same vocabulary is used in both places.

5.5. **Accessible by construction** (`STU-011`). Semantic elements first, Base UI primitives for composite widgets, a visible focus ring from tokens, an accessible name for every control, and labels from the message catalogue. No `div` with a click handler; no positive `tabindex`. Every drag has a keyboard alternative.

5.6. **Keyboard first.** Every action is reachable by keyboard. Arrow keys inside lists, menus and trees follow the reading direction (§8.4).

5.7. **Commands are registered once.** Every user-invocable action is a command in the command registry: ID, message key for its label, shortcut, availability predicate and handler. The command palette (`STU-013`, built on Base UI Dialog and Autocomplete), the shortcut sheet (`?`), menus and toolbars are generated from the registry; no shortcut is bound anywhere else. A test checks for duplicate shortcuts per scope.

5.8. **No `dangerouslySetInnerHTML`**, no `innerHTML`, no `eval`-like APIs (§11).

## 6. State and data

6.1. **Two kinds of state** (`STU-004`). Server state lives in TanStack Query (through Connect Query), keyed by resource and document revision. Local UI state lives in component state or one small Zustand store per area, created inside the area's React provider. No module-level mutable state (AGENTS.md §8). Live streams write into the area's store, not into the Query cache.

6.2. **Edits are JSON Patch.** Document edits are applied optimistically and autosaved as JSON Patch (`SRV-030`) with a 500 ms debounce by default (`STU-004`); a rejected patch rolls back and shows the diagnostic. Pending edits flush when the tab is hidden, through the generated client with a `keepalive` fetch transport.

6.3. **Undo is a model, not a feature of each component** (`STU-069`): every edit goes through one edit pipeline (Zustand + Immer) that records the forward and the inverse patch. A component never mutates the document directly. The pipeline is the single stream that feeds autosave, undo, the validator worker and the canvas worker. Undo applies the inverse patch as a new write; after a reload the stack is rebuilt from the server's snapshots of the editing session, never from browser storage.

6.4. **Contracts are generated.** Types come from `@plux/schema` and the Connect-ES clients in `@plux/api`; a hand-written duplicate of a contract type is rejected.

6.5. **Errors are reasons, not strings** ([error-handling.md](../engineering/error-handling.md)). The UI branches on the error reason and shows the localised message for that reason; it never parses `message`. Diagnostics show their code and JSON path and link to the node.

6.6. **Limits come from the registry** (`LIM-001`): editors read limits from `@plux/schema`'s generated limits; no size or count is hard-coded in the UI.

## 7. Studio localisation

Studio's own interface is localised and runs left-to-right and right-to-left (`STU-012`); the language is chosen in profile settings (`STU-014`). This section covers Studio's chrome. Localising the *apps users build* is spec §17 and is previewed on the canvas (§8.5).

7.1. **Locales.** Studio ships in English (`en`, the source locale), German (`de`) and Arabic (`ar`), which proves right-to-left layout (`STU-012`, ADR-0066 (to be written, C3)); Arabic is also the product's RTL launch locale (`I18N-002`). Adding a locale is data only: a catalogue file and an entry in the locale list, no code change.

7.2. **No literal UI text.** Every user-visible string — labels, placeholders, `aria-label`, `title`, tooltips, toasts, errors, empty states, document titles — comes from the message catalogue. A lint rule rejects string literals in JSX text and accessibility attributes with the first component. Product names (Plux, Plux Canvas) and user content are the only exceptions.

7.3. **ICU MessageFormat.** Messages use ICU MessageFormat with plural and select forms (as `I18N-001` requires for apps), through Lingui; plural rules, numbers, dates, relative times and lists use `Intl` with the active locale. No string concatenation to build sentences; no manual plural `s`.

7.4. **Messages are declared next to their feature** in `<feature>.messages.ts`: explicit stable key (`<area>.<feature>.<name>`), English source text and a description for translators (Lingui message descriptors). Catalogues per locale are compiled at build time from the declarations and the translations; strict extraction makes unused and missing keys fail `make studio-check`.

7.5. **Switching language** happens without a reload: the shell updates `<html lang>` and `<html dir>`, every mounted string re-renders, and focus stays where it was. The choice is stored in the user's profile on the server; before sign-in, the BFF negotiates from `Accept-Language`, and the user can override it on the sign-in page.

7.6. **Fallback.** A missing translation falls back `de-AT` → `de` → `en` and is reported in development and in tests; a key is never shown to a user.

7.7. **Pseudo-locales.** Studio ships two pseudo-locales in development and tests: accented and 40% expanded (`en-XA`), and mirrored right-to-left (`ar-XB`), matching what `I18N-010` gives app authors. Behaviour tests and the Playwright locale sweep run in `en`, `en-XA` and `ar-XB` (§12.4).

7.8. **User content is isolated.** App, plugin, screen and person names can be in any script; they are rendered with `dir="auto"` or `<bdi>` so a Hebrew app name in an English list, or a Latin name in an Arabic list, does not reorder the surrounding text.

7.9. **Studio's strings are managed like an app's.** The catalogues import and export as XLIFF 2.0 and JSON (`I18N-009`), so Studio's own translation can use the translation workflow Plux gives its users.

## 8. Direction (LTR and RTL)

8.1. **Logical properties only.** CSS and Tailwind use logical properties: `margin-inline-start`, `padding-inline-end`, `inset-inline-start`, `text-align: start`, `border-start-start-radius`; in Tailwind `ms-*`, `me-*`, `ps-*`, `pe-*`, `start-*`, `end-*`, `text-start`, `text-end`, `rounded-s-*`, `rounded-e-*`. Physical left/right properties and utilities (`ml-*`, `mr-*`, `pl-*`, `pr-*`, `left-*`, `right-*`, `text-left`, `text-right`, `float-left`) are rejected by a lint rule with the first component.

8.2. **Direction is read, never assumed.** Code that needs the direction (popover placement, drawer side, drag gestures) reads it from the direction provider (Base UI); no `dir === "rtl" ? … : …` scattered through components.

8.3. **Icons.** Studio's chrome uses one icon set, Phosphor duotone, through the `Icon` component (UI language U8). Icons with a direction (back, forward, chevrons, undo and redo arrows, "send", reply) mirror in RTL; icons without one (play, search, check, the Plux logo, clocks, media controls) never mirror. The set carries no mirror metadata, so the catalogue marks each icon `mirrors: true | false`.

8.4. **Keyboard follows reading direction in the chrome.** In lists, tabs, menus and trees, the "next" arrow key is Right in LTR and Left in RTL.

8.5. **The canvas does not mirror with the chrome.** The infinite canvas is a spatial design surface: its coordinates, the positions of screens and plugin boxes, rulers, zoom and keyboard nudging stay physical whatever the Studio language. What a device frame *shows* follows the **preview locale** (`STU-058`): an Arabic Studio user previewing an English screen sees it left-to-right, and the reverse. Studio direction and preview direction are two independent settings and are never derived from each other.

8.6. **Panels mirror.** The docked left and right panels swap sides in RTL; the spec's "left panel" and "right panel" (`STU-061`, `STU-062`) mean *start* and *end* panels.

8.7. **Numbers, code and identifiers stay LTR.** JSON, PXL, Rust, IDs, URLs, version numbers and keyboard shortcuts are rendered in an LTR-isolated span inside RTL text. Monaco and CodeMirror editors are always LTR.

## 9. Plux Canvas

9.1. **Off React's render path and off the main thread** (`STU-003`). React renders panels and chrome; the canvas renders the scene in its own loop in the canvas worker (§2.5). A property edit reaches the scene only as JSON Patch from the edit pipeline (§6.3), never through React props.

9.2. **The scene is queryable.** The canvas exposes a read-only scene model — nodes, frames, bounds, arrows, lanes, anchors, selection, z-order — for tests and for accessibility, as an asynchronous snapshot on the main thread fed by the worker's back channel. Tests assert on the scene model; nothing reads pixels back from WebGL to decide whether a test passes.

9.3. **Layout is proven by conformance vectors** (`STU-005`): positions and sizes compared with headless Flutter within the defined tolerance, across device frames, locales and text scales. The canvas is never "fixed" by tweaking it until it looks like the device.

9.4. **Text metrics** use the device's font files and SkParagraph through CanvasKit, built from the Skia revision the pinned Flutter uses, so line breaks and metrics match the device; where metrics are still not guaranteed (for example a substituted font), the canvas says that the device preview is authoritative (`STU-006`). Apple's SF Pro is never served by Plux: it comes only from the user's own installation through the Local Font Access API, otherwise a substitute is used.

9.5. **The canvas is accessible.** The scene model drives an accessible tree (a parallel DOM of focusable items with names) so screen readers and keyboard users can select, move and inspect nodes (`STU-011`).

9.6. **Context loss is handled.** WebGL context loss is expected: the canvas rebuilds its GPU resources from the scene model without losing the selection or the view.

9.7. **Design surface, not a runtime** (`STU-068`). Actions that navigate, call networks or functions are never executed on the canvas.

## 10. Performance

10.1. **Budgets are requirements**: 60 fps pan and zoom with 100 screens or 200 plugins (`STU-120`, `STU-045`); property change on the canvas within 50 ms p95 (`STU-121`); Largest Contentful Paint ≤ 2.5 s and initial JavaScript < 1.5 MiB compressed (`STU-122`); overlay open ≤ 150 ms after load (`STU-123`).

10.2. **Each budget has a benchmark** in CI from the change that first affects it. CI runs without a GPU: it tracks GPU-independent costs (layout time, draw-call count, CPU time per frame) and fails on a regression over 10% against its baseline (`QA-007`). Frame-rate budgets are confirmed on the reference laptop (spec §30.1) before each release and recorded in `docs/benchmarks/`. A performance claim without a benchmark run in the same session is not made.

10.3. **Code splitting.** Areas, overlays, Monaco, CodeMirror, the validator and the canvas load on demand; the canvas is prefetched while the apps grid is open. A new dependency in the initial bundle states its compressed size in the pull request; the bundle-size check fails over budget.

10.4. **Overlays preserve the canvas** (`STU-063`): opening one pauses the canvas without unmounting or re-rendering it; closing restores zoom, scroll and selection exactly.

10.5. **Measure before memoising.** `memo`, `useMemo` and `useCallback` are added where a profile shows they pay for themselves, and the pull request says so.

10.6. **Static assets are cheap to serve.** Hashed files are cached for a year as `immutable` and served Brotli-precompressed from the build; `index.html` is `no-cache`; no service worker.

## 11. Security

11.1. **No credential reaches JavaScript** (`SEC-101`, `STU-002`): the server issues the `__Host-plux_session` cookie (`HttpOnly`, `Secure`, `SameSite=Strict`) and the CSRF token (ADR-0026); the stateless BFF passes them through and keeps no session store; CSRF token on state-changing requests.

11.2. **Strict CSP with nonces and Trusted Types.** No inline scripts or styles without the nonce; `script-src` allows `'wasm-unsafe-eval'` (never `'unsafe-eval'`) for CanvasKit and the validator; `worker-src` allows Studio's own workers; Monaco and workers are loaded in a way the policy allows; Base UI receives the nonce through its `CSPProvider`; Zod runs with `jitless: true`; no `eval`, `new Function` or string timers, in our code or a dependency's.

11.3. **Everything pasted, imported or dropped is untrusted** (security-practices §3): clipboard content (`STU-067`), `.plux` archives, templates, OpenAPI files, images and translation files are validated by the API before use and never rendered as HTML.

11.4. **Sensitive fields** (`SCH-012`) are masked in editors, excluded from logs, telemetry and error reports, and never copied into URLs, the clipboard or browser storage in clear.

11.5. **No third-party scripts, fonts or analytics at runtime.** Everything Studio loads is served by the installation (air-gapped installs, P9). Telemetry goes only to the installation's own BFF and logs; it is sampled, rate-limited and can be switched off by an administrator.

11.6. **Step-up and type-to-confirm** for destructive and production actions (`STU-074`, `SEC-103`) are implemented once, as shared components, never per feature.

11.7. **Language servers are sandboxed.** rust-analyzer runs in the function build sandbox with build scripts and procedural macros off, no network and resource limits, one sandbox per session.

## 12. Testing

12.1. **Levels.**

| Level | What it proves | Location | Runs |
|---|---|---|---|
| Unit | Pure logic: models, safety rules, arrow routing, layout maths, formatting | next to the code, `*.test.ts` (`bun test`) | `make studio-cover` |
| Component | A component's behaviour through the DOM: roles, names, states, keyboard | next to the code, `*.test.tsx` (`bun test` + happy-dom + Testing Library) | `make studio-cover` |
| Contract | Studio against the generated Connect-ES clients with an in-memory transport | next to the hook | `make studio-cover` |
| Layout conformance | The canvas engine against headless Flutter (`STU-005`), CanvasKit headless under `bun test` | `test/layout-conformance/` | CI |
| Locale sweep | Every catalogue component and feature root in `en`, `en-XA`, `ar-XB`: overflow, direction, missing strings (§12.4) | Playwright over the catalogue page | CI |
| End-to-end | A user flow in a real browser against the Compose stack | `test/e2e/studio/` (Playwright) | CI |
| Performance | The budgets of §10 | `test/bench/studio/` (Playwright traces) | CI |

12.2. **Assert on meaning, not appearance.** Queries use roles and accessible names ("the button named *Publish*"), never CSS classes, test IDs on everything, or DOM structure. A test that would pass with the wrong label is wrong.

12.3. **Requirement IDs in test names** in the bracket form ([testing.md](../engineering/testing.md) §3): `test("blocks deleting a screen with incoming links [STU-070]", …)`.

12.4. **Every component is checked in three locales**: `en`, `en-XA` (expanded) and `ar-XB` (RTL). Behaviour tests run in all three. Text overflow (content size against box size) needs real layout, which happy-dom does not compute, so it is checked by the Playwright locale sweep over the catalogue page for every catalogue component and feature root. A check fails when text overflows its container, when a physical-direction style is applied, or when a string is missing from the catalogue.

12.5. **Accessibility checks are automated**: every component test also checks names, roles and focus order; Playwright runs axe in both themes and in RTL; end-to-end flows are run keyboard-only once per flow.

12.6. **Visual regression is CI-only.** Where a pixel comparison is the only possible oracle (the canvas renderer itself), CI compares images with a tolerance and reports the numbers. The images are artifacts for humans; agents read the numeric result, not the images (§13.1).

12.7. **Coverage floors** for `studio` are in `coverage.json` and are never lowered (`QA-001`).

## 13. Agent rules: context and token budget

Frontend work is where agents waste the most context: screenshots, page dumps from browser tools, and reading whole component trees. These rules keep Studio work cheap and verifiable. They apply to every agent session that touches `studio/`, and to humans directing agents.

13.1. **No screenshots without approval.** An agent does not take, request or read screenshots, screen recordings, rendered images of the UI, or image files (PNG, JPEG, WebP, GIF, AVIF) while working on Studio. An exception needs the maintainer's explicit approval **in the current session**, stating what the image is for; approval covers that one purpose only. Cases where asking is reasonable:
   - a canvas rendering defect that cannot be observed through the scene model (§9.2);
   - a CI visual-regression failure whose numbers do not explain it (§12.6).

   Even with approval: one image at the smallest size that shows the problem, cropped to the region, never a full-page capture. Visual review is the maintainer's: they pull the branch and run Studio locally.

13.2. **Verification is textual.** An agent proves a UI change with, in order of preference: unit tests, component tests (§12), scene-model assertions, end-to-end tests with role-based assertions, and the accessibility tree as text.

13.3. **Browser tools write to files.** Browser automation runs through the test runner or a command-line driver whose snapshots, traces and logs go to files under the session's scratch directory; the agent reads only the failure messages. Tools that stream full DOM snapshots or images into the conversation after every step are not used.

13.4. **Read narrowly.** Start from the spec map (§2.4) and the feature's README (§3.2); search before opening a file; open line ranges, not whole files, when the location is known; never read whole directories. Do not read `bun.lock`, `*.gen.ts`, `*_pb.ts`, coverage output, build output or `node_modules` unless the task is about them.

13.5. **Quiet commands.** Run `make` targets and tests with reporters that print failures only; on failure, read the first error before rerunning. Do not paste long logs back into the conversation.

13.6. **Reuse first, by catalogue.** Read `studio/packages/ui/CATALOGUE.md` before writing markup; a shared component is used by name instead of re-writing its classes.

13.7. **Design input as text.** Designs reach agents as text: tokens, the catalogue, the UI language, the reference page as HTML source, written specs, measurements and annotated wireframes in Markdown or SVG source. An image mock-up is converted to such text by a human before an agent works from it, or falls under §13.1. Every session that changes Studio's interface loads the design skill (`.claude/skills/plux-studio-design/`, drafted in [p11-studio-design-skill.md](p11-studio-design-skill.md)).

13.8. **One feature per session.** An agent session works on one feature folder and the shared packages it needs; work that spreads across areas is split into sessions, each starting from the work log.

## 14. Definition of done for a Studio change

In addition to [workflow.md](../engineering/workflow.md) §6:

- [ ] `make studio-check` passes; any benchmark the change affects ran and is within budget.
- [ ] Tests name their requirement IDs; behaviour tests run in `en`, `en-XA` and `ar-XB`, and the locale sweep passes; strings exist in `en`, `de` and `ar`.
- [ ] No literal UI string, raw style value or physical-direction property was added.
- [ ] Every new string has a key, English text and a translator description; German and Arabic are provided or tracked.
- [ ] The feature README and, for shared components, the catalogue entry and cases are current.
- [ ] New commands are in the command registry with a shortcut-collision check.
- [ ] Keyboard-only use and screen-reader names are covered by tests.
- [ ] Any new server work is bounded (§1.7) and any new dependency is on the allowlist.
- [ ] The interface is built from catalogue components in the UI language; the design skill's checklist is complete.
- [ ] No screenshot was used, or the maintainer's approval and its purpose are noted in the pull request.
