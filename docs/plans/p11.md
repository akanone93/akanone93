P11 builds Plux Studio: the browser application in which an app is designed, wired, previewed on a
paired phone, approved and released without leaving Studio. It is the largest phase: 97 rows tagged
P11 (88 of them `STU-`), plus the Studio halves that P2–P10 left `WIP` (§3.3). The riskiest part is
**Plux Canvas** — a WebGL design surface that must lay out every widget exactly as Flutter does on
the device (`STU-005`). P11's end-to-end flow is also the trigger for the first release, **0.0.1**
(spec §5 rules `BND-000`, `SCH-000`, `SRV-000`; plan p7 C6): from then on the bundle format, the
document schema and the API only grow additively.

This plan is the single entry point for P11. It does not repeat the preparation documents; it
binds them into one ordered programme, records what changed since they were written, lists every
requirement with the step that closes it, and records every decision taken for it.

---

## 0. For the session that starts P11

1. Read `AGENTS.md`, `docs/WORKLOG.md`, this plan, then only the preparation-document sections the
   current step names; run `git status` and `git branch --show-current`.
2. Work on `feat/phase-11`. When the maintainer reports that P10 is merged, merge `main` into it
   (no rebase) and re-check the registry allocations of §2.4 against `main`.
3. Start with S0.0 (decisions and contracts) and S0.8 (the canvas prototype) together: S0.8 is the
   riskiest work and decides whether the canvas design holds (§6).
4. Every session that touches Studio's interface loads the design skill (installed in S0.2) and
   follows rule book §13: no screenshots, verification as text, narrow reads, one feature per
   session.
5. Work as [sub-agents.md](../engineering/sub-agents.md) says: the lead creates each worktree from
   `feat/phase-11` (`git worktree add -b p11/<slice> .claude/worktrees/<slice> feat/phase-11`),
   writes pre-digested briefs of about 30 tool calls each, fixes the shared seams (contracts) before
   a fan-out, reviews every diff, runs `make gen`, merges and pushes. Agents never reformat
   generated files.
6. Stop and ask before anything in §2.3 or AGENTS §7 that this plan does not settle.

## 1. Goal and exit criteria

**Goal (spec §5.1):** Studio shell, design system and themes; Plux Canvas with a Flutter-compatible
layout engine and conformance suite; apps grid; plugin graph with bundled arrows; plugin canvas with
ghost screens; no-code project generation and shell-update detection; screen editor with panels,
full-screen overlays and bottom drawer; multi-device frames; components and templates; release,
approval, experiment, function, localisation, design system, data, analytics, device and admin
screens.

| # | Exit criterion | How P11 proves it |
|---|---|---|
| X1 | A complete app is built in Studio alone, previewed on a paired device, approved and released (spec §5.1) | The exit demo (F23): from a blank app → screens, navigation, data and a function → sent to a paired device → publish flow → approved by a second person with WebAuthn step-up → released with a staged rollout. ### 6.2 Permissions for Studio commands (M-7)

1. **One source.** The server's catalogue (`backend/internal/auth/permissions.json`, `roles.json`)
   is the only list of permissions. `make gen` writes it for Go (as today) and, from S0.5, for
   TypeScript into `@plux/schema`.
2. **Every command declares its permission.** A command in Studio's registry names the permission
   of the RPC it calls, typed against the generated catalogue, so an unknown name does not compile.
   A test fails for a command without a permission and lists, for review, every command next to its
   permission (rule book §5.7, F14).
3. **A missing permission is added in the same change, server first.** When a new command's action
   is not covered: the permission is added to `permissions.json` with its area, feature, action and
   risk, given to the roles that should have it in `roles.json`, checked by the server in the RPC's
   handler (deny by default, `SEC-102`), covered by the authorisation-matrix test for every role
   (`backend/internal/api/authz_matrix_table_test.go`, `QA-008`), and listed in the change for the maintainer's approval (AGENTS §7). Only then does the
   Studio command use it.
4. **Interface restrictions are named as such.** A switch that only shapes the interface (for
   example, hiding the JSON tab from a role that may still edit through Properties) is a profile or
   organisation setting, never a permission, and the documentation says it is not a security control.
5. **Showing it.** Studio hides what the effective permissions never allow and disables, with the
   reason from `ExplainAccess`, what is denied only here or now (F14); the server checks every call
   regardless.
6. **Each slice's contract step** lists the permissions its commands need and the new ones it adds;
   S0.0 starts the list from the routing file's pages and dialogs.

## 8. Testing strategy (spec §28, `testing.md`, rule book §12)

- Every requirement named in a test (`[STU-070]` bracket form); `make trace` stays at 0 violations.
- Levels: unit (models, safety rules, arrow geometry, layout maths), component (DOM roles and names,
  keyboard), contract (Connect-ES with an in-memory transport), layout conformance, locale sweep,
  end to end (Playwright against the Compose stack), performance.
- Assert on meaning: roles and accessible names; the canvas through its scene model, never pixels.
- Security: no credential in JavaScript, storage or URLs; CSRF on every state change; CSP and
  Trusted Types violations fail tests; clipboard and imports as untrusted data; sensitive fields
  masked; authorisation matrix entries for every new RPC and permission; the language-server
  sandbox escape tests.
- Permissions (§6.2): every command declares a catalogue permission; every new permission has its server check and authorisation-matrix rows for all eight roles.
- Concurrency and resilience: two `api` replicas sharing one dev session (S0.9); two tabs and two users on one plugin (locks, takeover, conflicts);
  offline and server restarts with stream resume; WebGL context loss.
- Determinism: the `canvas` document never changes a compiled bundle; the Studio build reproduces.

## 10. Risks

| Risk | Mitigation |
|---|---|
| The layout port drifts from Flutter (`STU-005`) | Port from the pinned source file by file with the revision recorded; conformance from S1, not at the end; a Flutter upgrade regenerates goldens and the diffs are ported |
| CanvasKit size and its custom build (emsdk, Skia toolchain) | S0.8 measures first; the canvas loads on demand, prefetched while the apps grid is open; the build is pinned and cached in CI |
| Worker WebGL missing or slow in Firefox or Safari | S0.8 tests all three engines; the main-thread fallback; "unsupported browser" only without WebGL2 |
| The Go validator in WebAssembly is large (3.1 MiB gzip) or slow | Loaded only with an editor; batched messages; split validation from encoding; TinyGo; project-wide checks on the server as the last resort (A4.7) |
| 60 fps unproven on real hardware | GPU-independent costs gated in CI; the reference-laptop run before the exit (M-4) |
| rust-analyzer runs user code | Build sandbox, build scripts and procedural macros off, no network, resource limits, one sandbox per session, audit (A5.3) |
| Contracts frozen by 0.0.1 | Every contract additive and reviewed per slice (L-6); `buf breaking` from 0.0.1 |
| Legal reviews still open (O-7) | Release conditions in the ADRs; nothing published until closed |
| Scope: the largest phase | Steps sized for one brief; waves in parallel; the exit gate per slice; replay last and deferrable (O-8) |
| TypeScript 7 and Vite plugins (the workspace pins `typescript` 7.0.2) | S0.1 verifies every plugin and type-checks the whole workspace; if a plugin needs the TypeScript 5 API, that is put to the maintainer before any workaround |
| Agents burning context on UI work | Rule book §13 and the design skill: text-only verification, catalogue first, narrow reads |
| Dev sessions across `api` replicas (O-20) | Step S0.9 (M-8): no session state only in memory; the two-replica tests and benchmark; until it merges, the documented one-replica limit |
| N+1 calls from the apps grid and the app canvas (200 boxes) | Bounded summary RPCs (§4.3 #14); registry page sizes; BFF rate limits |

## 11. Process

- [sub-agents.md](../engineering/sub-agents.md) is the playbook: the lead creates the worktree
  from `feat/phase-11` (never automatic worktree isolation), writes a pre-digested brief (worktree,
  READ with line ranges, PATTERNS, BUILD, RULES, TESTS, DONE-CHECK, commit message), commits the
  shared seams first, runs independent slices in parallel without two editing one file, reviews
  and merges every diff, and pushes after each merged slice; agents do only the brief, commit, run
  the done-check once and report in at most eight lines (AGENTS §6).
- Model tiers (sub-agents.md, L-15): **small** for mechanical work (translations, catalogue cases,
  registrations, documentation), **standard** by default, **high** only for security,
  cryptography, migrations and concurrency-critical code (the BFF, locks, autosave, undo storage,
  change sets, the language-server sandbox, release requests, the dev-session fan-out); **lead**
  for decisions, contracts, reviews and gates.
- One feature folder per session (rule book §13.8); every Studio UI session loads the design skill.
- The lead updates `docs/WORKLOG.md` at the end of every step and keeps the task list current.
