# Phase 10 plan — Dev app and live debugging

| Item | Value |
|---|---|
| Phase | P10 — Dev app and live debugging (spec §5.1), first phase of milestone M3 — Plux 1.0 |
| Status | Proposed 2026-10-22; maintainer decisions taken the same day (§2.1) |
| Branch | `feat/phase-10`, cut from `main` once P9 is merged (§0) |
| Specification | 1.8.0 → 1.9.0 in milestone D0 (§4.1) |
| Previous plan | [p9.md](p9.md); analysis [p10-analysis.md](p10-analysis.md) |

P10 lets a developer see a Plux page change on a real phone half a second after saving it,
and watch everything the page does while it runs: logs, the action flow, state, network and
function calls, sync and frame timings. It delivers the Plux Dev app, the same capabilities
inside a developer's own debug build through `plux_devtools`, the server's dev-session relay,
incremental compilation, and a terminal workflow (`plux dev`) that stands in for Studio until
P11. Nothing of it may exist in a release build. P10 also delivers two items earlier phases
deferred here: opt-in background sync (`SYN-014`) and starter flavours per router.

pairing; live draft push with incremental compile; streaming of logs, action traces (process
flow), state, network, function calls, sync and performance; on-device inspect mode; mocks

### 2.2 Decisions the maintainer delegated to the lead (2026-10-22)

- **Event schema:** protobuf messages (`proto/plux/v1/devevents.proto`), sent as binary
  WebSocket frames, one event per frame, each with a session sequence number.
- **Trace file:** a gzip-compressed stream of length-prefixed `DevEvent` protobuf messages
  with a header message (format version, session, app, environment, export time); `plux dev
  trace show` and later Studio read it. Exported traces are redacted like the stream.
- **Pairing token:** a compact signed token (the development token key, through `signing`)
  carrying session ID, user, app, environment, expiry and a single-use nonce; the QR holds
  `plux-dev://pair?server=<url>&token=<token>`; the token's hash is stored and consumed in
  one transaction.
- **Device authentication on the socket:** the device pairs over unary ConnectRPC with DPoP
  (`SEC-021`); the pair call returns a short-lived session-bound socket ticket, presented
  once at the WebSocket upgrade, bound to the device's DPoP key thumbprint; the socket
  closes on session end, ticket expiry or revocation.
- **Hot apply:** the compiler emits, per patch, a state-compatibility verdict per page
  (same state schema, or a list of incompatible scopes); the runtime keeps compatible
  scopes and resets the rest, saying so in the stream.
- **Network simulation on the device:** a debug-only wrapper at the runtime's HTTP client
  seam; the profiles (offline, 2G, 3G, high latency, packet loss, good Wi-Fi) are defined
  once in `schema/devtools/network-profiles.json` and generated for Go (netsim) and Dart.
- **Limits** (registry keys, §2.4) with moderate defaults, confirmed at D0 review.

## 5. Architecture

### 5.0 Starting point (surveyed 2026-10-22, `p10-analysis.md` §2)

Nothing of the dev session exists on the server, in the protos or in the CLI. The runtime
has `PluxDiagnostics` (`devtools_api/diagnostics.dart`: problems, release, sync status,
action traces in a bounded redacted ring buffer), data mocks with states, an injectable
action clock, the dev-bundle source map (`CMP-041`), and a `dart:io` WebSocket transport.
`plux_devtools` 0.1.0 is a 315-line debug overlay. `make release-inspect` runs in CI for
Android and iOS. `internal/netsim` simulates networks for server benchmarks.
`apps/plux_viewer` is the reconstruction viewer (production roots).

### 5.1 Incremental compilation (D1) — ADR-0089

- `backend/internal/compiler/incremental`: a `Cache` value owned by the caller (worker or
  CLI), keyed by content hash of each document plus the hashes of everything it references;
  the reference graph (`compiler/refgraph.go`) gives the dependants. An edit invalidates the
  edited document and its transitive dependants only (`CMP-051`).
- The compiler stays a pure library (L-5): no I/O, the cache injected. Output is
  byte-identical to a full compile (`CMP-002`); the property test compiles a generated edit
  sequence both ways and compares bytes.
- The result carries the changed sections and the per-page state-compatibility verdict
  (§2.2). A first latency measurement lands here: one-page edit of a 50-page plugin at
  most 100 ms p95 on the CI runner.
- D1 also closes D-10 if P9 has not: the sync update size back under its baseline.

### 5.2 The dev session service (D2) — ADR-0087

- `backend/internal/devsession` (spec §6.3), thin handlers (L-1). Sessions only for
  environments whose kind is not production (`DEV-003`, `PLX-9203`); creation needs
  `devsession.create`, and step-up when the organisation's policy says so (D-5).
- Pairing (`DEV-002`): the token of §2.2, at most `devSession.pairingTokenSeconds`, single
  use (hash consumed in a transaction), bound to the creating user, app and environment;
  several devices per session up to `devSession.devicesPerSession`. The device pairs over
  ConnectRPC with DPoP and, where the platform gives it, development attestation; the reply
  carries the socket ticket.
- Patches (`PushPatch`): the document patch is validated, compiled incrementally on the
  worker (no signing capability there, L-4), the sections are signed by `signing` with the
  development class (L-3) and pushed to every paired device of the session.
- Relay: per-device bounded queues (registry limits), backpressure, fan-out; commands are
  authorised per device; every state change audited; the CLI reads events through
  `WatchEvents` (server stream) and exports traces through `ExportTrace`.
- Function logs (D-7): the relay joins the device's function-call events with
  `fnrunner` logs by trace ID for the session's own app and environment.
- Chart: the api role's ingress allows the WebSocket upgrade with an idle timeout from
  configuration; the NetworkPolicy already admits device traffic to the api role.

### 5.3 Runtime dev channel and hot apply (D3)

- In `devtools_api`, behind `kDebugMode` and a `bool.fromEnvironment('plux.devtools')`
  constant so release builds tree-shake it (`DEV-050`). The socket, verification, patching
  and event encoding run in a background isolate (L-6).
- Dev bundles are verified before load (`SEC-052`) against the pinned development roots
  (D-2), applied to a session overlay over the active release; the production store is
  never written; ending the session discards the overlay.
- Hot apply (`DEV-010`): re-render the changed pages; keep the state scopes the verdict
  marks compatible, reset the others and report `PLX-9231` in the stream.
- Commands (`DEV-011`, `DEV-031`): open a screen with parameters, locale (including the
  pseudo-locale), theme and text scale; set a state value; switch a data-source mock and its
  state (`DAT-080`); fake the clock (the injectable `ActionClock`); trigger lifecycle events;
  simulate a `plux_security` detection (D-8).

### 5.4 Device streams (D4) — ADR-0090

- Event types: log, action trace (the process flow, `ACT-030`), state diff (bounded by
  `devtools.stateDiffBytes`), network call (method, URL template, status, timings; bodies and
  headers redacted by default), function call (`FN-036`), sync event, frame timing, error
  with node path (the source map), `plux_security` detection (D-8).
- Redaction at the source (`ACT-031`, `SCH-012`): sensitive values never leave the device,
  even in development.
- Bounded ring buffers with drop counters; pausing keeps buffering up to the bound;
  resumable by sequence number after a reconnect (`DEV-021`).

### 5.5 Inspect, overlays, console, screenshots, network simulation (D5)

- Inspect (`DEV-030`): a hit test maps a render object to the Plux node index and, through
  the source map, to the document path; the device highlights a node a client selects.
- Overlays (`DEV-034`): frame chart and rebuild counters (from `FrameTiming` and the
  renderer), touch-target and contrast highlights using the compiler's thresholds.
- PXL console (`DEV-032`): evaluates an expression against the live state of a paired
  device, read-only by default, through the existing interpreter.
- Screenshots (`DEV-033`): `RepaintBoundary` capture of the current page; platform views are
  marked as not captured.
- Network simulation (`DEV-031`): the HTTP wrapper of §2.2 with the shared profiles.

### 5.6 `plux_devtools` in host apps (D6) — ADR-0091

- The pairing client (QR scan or pasted link), the command and stream adapter over the D3
  API, and the overlay, so a developer's own debug build has the Dev app's capabilities
  (`DEV-040`). Debug builds only; the starter app wires it.

### 5.7 The Dev app and the host kit (D7) — ADR-0093

- `packages/plux_host_kit`: sign-in (device grant or token), link handling, root-key pinning
  and the release opener, extracted from `apps/plux_viewer` without behaviour change.
- `apps/plux_dev`: a host on `plux_flutter`, `plux_devtools` and `plux_host_kit`, Android and
  iOS, with every first-party optional package (`DEV-001`), `plux_security` in its development
  mode (D-8), QR scanning through `plux_scanner`, pinned development roots, and experiment
  previews (P9 hand-off).

### 5.8 The CLI as Studio's stand-in (D8)

- `plux dev`: creates the session, shows the pairing QR (or link and code, §2.3), watches
  the project files, sends each saved change as a patch and prints the apply result per
  device.
- `plux dev logs [--app --env --device --filter --json --since]` (`DEV-041`), `plux dev
  trace export|show` (`DEV-021`), `plux dev open <route> [--param --locale --theme
  --text-scale --mock]` and `plux dev set|mock|clock|lifecycle|network|security-detect`
  (`DEV-011`, `DEV-031`, D-8). Every command reads the effective permissions (`GOV-007`).

### 5.9 Release absence and the latency benchmark (D9)

- `make release-inspect` gains the P10 symbols (transport, event schema, hit test, simulator,
  commands, `plux_host_kit` dev roots) and canary strings compiled only into debug code.
- `make bench-devloop` (X1), nightly; `docs/benchmarks/devloop.md` records the method and
  results.

### 5.10 Quick start and the scripted session (D10)

- The quick-start guide (`docs/guides/quick-start.md`) from `flutter create` to a published
  page, using the starter flavours (D11) and `plux dev`; a timed scripted dry run
  (`make quickstart-dry-run`) in CI; the recorded sessions are the maintainer's (§3.2).
- `test/devloop/`: the X2 scripted debugging session.

### 5.11 Background sync and starter flavours (D11) — ADR-0092

- `SYN-014`: opt-in through `PluxConfig.backgroundSync`; Android uses WorkManager
  (`androidx.work`, §2.3) with network and battery constraints, iOS uses
  `BGAppRefreshTask` through `BGTaskScheduler` with the identifier the host declares in its
  `Info.plist`. The task runs the existing sync worker headless, verifies and stages the
  release (never activates it), and respects `sync.backgroundIntervalMinutes`. Codes
  `PLX-3500`–`3509`. Tests: Dart unit tests of the headless entry, Kotlin and Swift unit
  tests of the schedulers, and device tests in the emulator/simulator jobs.
- Starter flavours: `plux create --router go_router|auto_route|none` (and the starter app's
  flavours) wire `plux_go_router` or `plux_auto_route`; each adapter's example stays.

## 8. Testing strategy (spec §28, `testing.md`)

- Every requirement named in at least one test (`make trace`).
- Security: pairing token expiry, reuse, wrong environment and wrong user; socket ticket
  replay and thumbprint mismatch; a production runtime refusing a dev bundle (`SEC-056`);
  commands refused to an observer; redaction of sensitive values in every event type; the
  release inspection's canaries.
- Determinism: incremental equals full compile, byte for byte, over generated edit
  sequences (property test, fuzzed).
- Concurrency: the relay with many devices and slow consumers under `-race`; the runtime's
  background isolate and overlay discard.
- Latency: `bench-devloop` (X1); the server part measured separately so regressions are
  attributable.
- Device: hot apply, inspect and overlays in widget tests; pairing and the dev loop on the
  emulator job; background sync on emulator and simulator.

## 10. Risks

| Risk | Mitigation |
|---|---|
| 500 ms p95 not met (compile, signing, device apply) | Measure in D1 first; budgets per stage (server ≤ 120 ms, device apply ≤ 150 ms); the server part reported separately |
| Debug code leaking into release builds | Compile-time constants, tree shaking, extended `release-inspect` with canaries on both platforms (X3) |
| A remotely drivable device (state edits, clock, PXL) | Debug or Dev-app builds only, pinned dev roots, session-bound socket tickets, per-device authorisation, audit, rate limits, no production environments |
| Sensitive data in streams and trace files | Redaction at the source; bodies and headers off by default; trace files redacted the same way |
| Long-lived sockets through ingress and proxies | Ingress idle timeout and upgrade settings in the chart; reconnect with resume by sequence number |
| iOS background limits (`SYN-014`) | `BGAppRefreshTask` is best-effort; the feature stages only and never relies on running |
| Emulator-only device CI (ADR-0035) | Radio latency not representative; the benchmark uses netsim profiles and states its method |
| P9 not merged when P10 starts | D-11 |

## 11. Process

- The P9 playbook: agents in worktrees from self-contained briefs, the smallest model that
  does the job (Haiku for mechanical work, Sonnet otherwise, high effort only for security,
  native, concurrency or migrations), the lead reviews every diff, fixes and merges, runs
  `make gen` and the gates, and owns CI. Agents never reformat generated files.
- The lead runs `make check`, `make trace`, the dispatched CI run and the benchmark at D12,
  updates `docs/WORKLOG.md` and the task list, and writes the pull request.
