# Phase 9 plan — Enterprise and operations

| Item | Value |
|---|---|
| Phase | P9 — Enterprise and operations (spec §5.1), milestone M2 — High-assurance |
| Status | Proposed 2026-10-18; maintainer decisions taken the same day (§2.1) |
| Branch | `feat/phase-9`, cut from `main` once P8 is merged |
| Specification | 1.6.1 → 1.7.0 in milestone E0 (§4.1) |
| Previous plan | [p8.md](p8.md) |

P9 makes Plux operable by a regulated organisation: who may do what (roles, single sign-on,
provisioning, step-up), who must agree before production changes (the approval engine),
how a change reaches devices safely (rollouts, targeting, the signed control document, the
kill switch, flags and experiments), what the organisation can see and prove afterwards
(telemetry, dashboards, alerts, audit export, "what did the user see", compliance reports),
and how it runs the whole thing (Helm, HA, backups, air-gapped installs, the enterprise
edition and its licence file).

## 1. Goal and exit criteria

**Goal (spec §5.1):** teams, roles and custom roles; SSO (OIDC, SAML) and SCIM; a generic
approval engine with four-eyes and step-up; break-glass; change freezes; environments and
promotion; staged rollouts, targeting, scheduling, health-based auto-pause and rollback;
kill switch; experiment and feature-flag engine; telemetry ingestion and dashboards;
observability stack; Helm chart; HA; backups; air-gapped install; licence files.

**Exit criterion (spec §5.1):** a self-hosted HA install passes a scripted regulated-industry
audit walkthrough: approvals, rollout, kill switch, rollback, audit export and "what did the
user see" reconstruction.

### 2.2 Decisions the maintainer delegated to the lead (2026-10-18)

**D-L — Licence files (`GOV-030`, `GOV-033`; Q8).**

- **Format.** A licence is a JSON payload in the same signed envelope the update metadata
  uses (ADR-0004): `{"licenseId", "organization", "edition": "enterprise", "issuedAt",
  "notBefore", "expiresAt", "graceDays": 30, "features": [...], "limits": {...},
  "installationId": optional}`. Features are named from the edition split (§2.6), limits
  from the limit registry (`LIM-001`) so a licence can only cap what the registry knows.
- **Signature.** Ed25519. The public keys are compiled into `ee/license` with key IDs, so a
  key can be rotated by shipping a new public key next to the old one. The private key never
  touches a server, CI or the repository: the maintainer holds it offline (a hardware token,
  or an encrypted file on an offline machine) and signs with `plux-license`, a small tool in
  `ee/cmd/plux-license` that is not part of any image.
- **Verification.** Offline only, never calling home: at start-up and every hour the server
  verifies the file named by `PLUX_LICENSE_FILE` (or the `license` Helm secret). Invalid or
  absent: the open-source core runs fully and every enterprise feature is off. Expired:
  `graceDays` of warnings (log, metric `plux_license_days_remaining`, an admin notice), then
  enterprise features turn read-only (existing data stays readable and exportable; nothing
  is deleted; no new writes through enterprise features). An installation over a licensed
  limit gets warnings and an audit entry, never refused device traffic.
- **Never gated (`GOV-032`).** Security capabilities, the audit log, the kill switch,
  rollbacks and break-glass work identically with or without a licence.
- **CLI.** `plux license inspect <file>` shows the payload and its verification result;
  `plux admin license` shows the installation's state.

**D-O — OIDC (`GOV-004`; Q18).** P6 already ships an in-house OpenID Connect client
(`backend/internal/auth/oidc.go`: discovery, authorization code flow with PKCE S256 and a
nonce, token verification through the existing `go-jose` dependency, account linking).
P9 extends it instead of adding `coreos/go-oidc`: several providers per installation and per
organisation, the `groups` (or configured) claim mapped to roles and teams, just-in-time
provisioning behind a setting, ID-token `acr`/`amr` recorded, and back-channel logout. No
new dependency; the extension stays in the core (OIDC is open source, §2.6).

### 2.5 Phase P16 — Super-app and partner mini-apps (Q3)

**The idea in two sentences.** A host organisation runs several Plux apps and web-based
mini-apps inside one binary, each isolated with its own bundles, state, storage, theme and
host-approved capabilities, and deeply integrated with the host's own plugin system. The host
organisation can also invite partner organisations as accounts with a detailed permission
model, which build and maintain their own (native-widget or web-based) mini-apps, submit them
for the host's review, and publish into the host's super-app only after the host approves, as
in the Asian super-apps.

Recorded in E0: spec 1.7.0 adds P16 to §5.1 (milestone M4, after P15, whose tenancy work it
builds on), retags `HST-020` to P16 and records the scope above in ADR-0072. P16 is planned
in its own plan with its own requirement IDs; it needs an ADR on web mini-apps against
`SEC-054` (downloaded executable code) before any web runtime work starts.

### 5.1 Roles, permissions and scoping (E1) — ADR-0073

- **Permission catalogue.** One generated catalogue (`auth/permissions.json` → Go, Dart, TS)
  lists every permission with its description, risk and whether it needs step-up; the
  documentation table is generated from it (`GOV-002`).
- **Predefined roles.** Owner, Admin, Release Manager, Developer, Designer, Translator,
  Reviewer, Compliance Officer, Auditor (read-only including the audit log, plus
  `reconstruction.view` and `audit.export`), Viewer. Migrations map today's roles
  one-to-one; nobody loses or gains access on upgrade (tested).
- **Custom roles (ee).** Composed from the catalogue; a custom role can never hold a
  permission the creator does not hold; changing a role needs step-up (`SEC-103`) and, when
  a policy says so, approval.
- **Teams.** Users belong to teams; approval policies use team membership (`GOV-021`
  distinct teams); SCIM groups map to teams.
- **Scoping (`GOV-003`).** A grant is `(principal, role, scope)` where scope is
  organisation, app, or app + environment; `release.publish:production` style permissions
  resolve through the scope. Every handler keeps calling `authorize`; the resolver changes,
  not the call sites (L-1). The authorisation matrix test (`QA-008`) is regenerated for the
  new roles × permissions × scopes.

### 5.2 Federation, sessions and step-up (E1) — ADR-0074, ADR-0075

- **OIDC (core).** D-O: several providers; group claim → role/team mapping documents;
  JIT provisioning (off by default; when on, a new person gets the mapping's roles only);
  `auth.studio.allowPasswordLogin` can be false once a provider exists.
- **SAML 2.0 (ee).** SP-initiated and IdP-initiated with `crewjam/saml`; signed assertions
  required, encrypted assertions supported; replay cache in Valkey keyed by assertion ID
  (`PLX-6211`); metadata import; clock skew bound from the limit registry.
- **SCIM 2.0 (ee).** `/scim/v2/Users`, `/Groups`, `ServiceProviderConfig`, `Schemas`,
  `ResourceTypes`; PATCH semantics; bearer tokens per organisation (hashed, rotatable);
  deprovisioning revokes sessions and tokens at once (`GOV-004`, `GOV-005`).
- **Sessions (`GOV-005`).** A sessions table (device, IP prefix, user agent, created, last
  seen); idle and absolute timeouts per organisation; administrators list and revoke
  sessions and personal tokens; revocation propagates through Valkey within seconds.
- **Step-up (`SEC-103`).** A WebAuthn assertion with user verification within the last
  5 minutes, recorded on the session as `stepUpAt`; actions in the catalogue marked
  `stepUp` (approve, production publish, key operations, role changes, secret changes,
  break-glass, licence and policy changes) require it (`PLX-6200`/`6201`). **CLI (Q15):**
  `plux` opens `https://<server>/stepup?request=<id>` in the browser; after the ceremony
  the server issues a 5-minute grant bound to the CLI's DPoP key thumbprint; the CLI polls
  with its DPoP proof. Tests cover expiry, replay and a grant used with another key.

### 5.3 The approval engine (E2) — ADR-0076

- **Policies (`GOV-020`).** `policy` documents, versioned and audited like any document,
  stored per organisation: `match` (resource type: release, function version, policy,
  security configuration, limit, capability set, experiment, waiver, golden baseline;
  environment; action; risk attributes such as `touchesSecurePage`, `touchesMoneyFlow`,
  `changesFunctionUsedBy`), `require` (approver count, roles, named approvers, distinct
  from author, distinct teams, stages sequential or parallel, expiry). Risk attributes are
  computed by the compiler and the release service from the diff (pages marked `secure`,
  flows with SCA steps, functions referenced by those flows).
- **Requests and binding (`GOV-022`).** A request names the artifact by content hash
  (release ID + manifest hash, function version hash, policy document hash). Any change
  creates a new hash and the old approvals stop counting (`PLX-8002`).
- **The review bundle (`GOV-023`).** JSON diff, validation and accessibility reports,
  golden-image diffs from P8's server-held baselines (the visual diff), the affected install
  base (devices on the current release, by channel and build), the changelog and a computed
  risk summary. Served through the API and `plux approvals show` (writes the diff images and
  an HTML summary locally).
- **Decisions.** Approve or reject with WebAuthn step-up; each decision is a signed record
  (the server's audit signing key, ADR-0019 style), appended to the audit log.
- **Break-glass (`GOV-024`).** Designated roles run kill switch, rollback or function
  disable without approval, with a written justification; approvers are alerted at once
  (E7 notifications); a post-hoc review is opened, due within the configurable window
  (default 24 h), escalating when overdue (`PLX-8006`).
- **Change freezes (`GOV-025`, ee).** Calendar windows (one-off and recurring, with time
  zones) per organisation and environment; production changes refused with `PLX-8010`
  except through break-glass.
- **Compliance reports (`GOV-026`, ee).** For a period: every production change with
  author, approvers, timestamps, content hashes and evidence; signed JSON (DSSE envelope)
  and PDF (in-house writer); verification with `plux compliance verify`.
- **Wiring the stand-ins.** Release promotion to production, function production deploy,
  device-function enablement, security-configuration changes, limit raises (`LIM-006`),
  capability sets (`SEC-080`), accessibility waivers, golden baselines, experiments on
  secure or money flows (`ABT-007`) and required tests (`TST-005`) all go through
  `approval.Require(ctx, artifact)`. Default policies per profile (Q16) are seeded and
  editable.

### 5.4 Control document, kill switch, mandatory update, silent push (E3) — ADR-0077

- **Document.** One control document per app, environment and channel: kill switches
  (plugin, page, action graph, data source, function) each with an optional targeting
  rule; flag values per segment (E5); running experiments and their allocations (E5);
  forced rollback (target release); mandatory update (release ID and message key). Encoded
  in FlatBuffers, wrapped in the update-metadata envelope, signed by the new online
  `control` role (ADR-0004 Revision), with a version that only increases and an expiry
  (default 24 h; configurable).
- **Device.** The runtime fetches it on resume and every 5 minutes in the foreground
  (`SYN-060`), with `If-None-Match` and DPoP; verifies before parsing (`SEC-052`); refuses
  older versions (`PLX-3102`); applies switches without restart (pages and plugins show
  their fallback `RT-022`; action graphs, data sources and functions fail with their
  documented error). When the document cannot be refreshed within its expiry, every kill
  switch it last carried stays in force (fail closed for switches only; the app keeps
  working).
- **Mandatory update (`REL-070`).** The device activates the release before showing any
  Plux page again, behind a host-customisable update screen (`PluxConfig.updateScreen`).
- **Forced rollback.** The device activates the named earlier release from its retained
  bundles (the anti-rollback rule allows a signed control-document rollback, ADR-0004
  Revision) and reports `control_applied`.
- **Silent push (Q22).** `Plux.handleSilentPush(Map payload)` (no push SDK in the runtime;
  the host passes the payload) triggers an immediate check. The server sends through the
  operator's FCM HTTP v1 and APNs credentials (secrets in the secret store), only data
  messages carrying no content, off by default, listed in the egress list.
- **Propagation (`NFR-024`).** Measured by `bench-control` (§7): time from a switch change
  to `control_applied` on 20 emulator instances, with and without push.

### 5.5 Rollouts and health gates (E4) — ADR-0078

- **Bucketing (`REL-050`).** `bucket = sha256(rolloutSalt ‖ subject) mod 10000`, where the
  subject is the user ID when `setUserContext` provided one (sent hashed) and otherwise the
  device ID; monotonic: a device in at 10% stays in at 50%.
- **Targeting (`REL-051`).** Evaluated on the server when the device fetches its manifest:
  the request carries build, runtime version, OS and version, device class, locale,
  region (from the device's setting, not IP), channel, and hashed or allowed user
  attributes; segments are documents; explicit allow/deny device lists for testers.
- **Schedules (`REL-052`).** Start, staged percentages with durations, end with
  auto-revert to the previous release; a scheduler in the `worker` role, idempotent,
  leader-elected through PostgreSQL advisory locks.
- **Health gates (`REL-053`, Q13).** The runtime reports `session_start`, `session_end`,
  `fatal_error` (Plux) and uncaught Flutter errors; E6 computes crash-free sessions, Plux
  error rate, action, function and custom-metric rates per release; the gate compares the
  candidate with the previous release over a minimum sample and pauses (`PLX-3150`) or
  rolls back (`PLX-3151`) per the rollout's thresholds, notifying through E7.

### 5.6 Flags and experiments (E5) — ADR-0079

- **Flags (`ABT-006`).** Typed (bool, number, string, JSON with a schema), defaults in the
  app document, per-segment values in the control document; PXL `flags.<key>`; generated
  host accessors (`plux codegen`), updated without a release; `NAV-009` flag guards
  evaluate targeting.
- **Experiments (`ABT-001`).** Scope: page, component subtree (`Variant` node), prop value
  (`experiment.<key>.<prop>` in PXL), flow (route mapping) or plugin version (channel
  split); control plus variants, allocation, targeting, schedule, primary and guardrail
  metrics, minimum sample size.
- **Compiled in (`ABT-002`).** Variants are in the release; assignment on the device:
  `variant = weightedPick(sha256(experimentSalt ‖ subject))`, sticky; the exposure event is
  recorded only when the variant's node actually builds (a hook in the renderer, not at
  assignment).
- **Layers and holdouts (`ABT-004`).** Layers partition traffic so experiments in one
  layer are mutually exclusive; a global holdout excludes a fixed share from all.
- **Analysis (`ABT-003`, Q12).** Rollups by variant from E6; always-valid confidence
  sequences (mSPRT with a normal mixture) for proportions and means; χ² SRM check at
  p < 0.001 flags the experiment (`PLX-8202`); CUPED with the 14 days before exposure as
  the covariate where it exists. Validated against simulated A/A and A/B data with known
  effects (type I error ≤ α under continuous peeking, tested).
- **Promotion (`ABT-005`).** `plux experiment promote <id> <variant>` creates a release
  whose compiler pass replaces each `Variant` by the winner's subtree and inlines
  `experiment.<key>` bindings (`PLX-2301`).
- **Approval (`ABT-007`).** Experiments touching `secure` pages or money flows under
  `maximum` go through E2.

### 5.7 Notifications, webhooks and function triggers (E7) — ADR-0081

- **Channels (`SRV-062`).** In-app inbox (API and CLI; Studio in P11), SMTP, Slack, Microsoft
  Teams and Telegram webhooks; per-user and per-team subscriptions to event types
  (approval requested, release published, rollout paused, lock requested, function failing,
  alert fired, break-glass used, licence expiring).
- **Outbound webhooks (`SRV-063`).** Standard Webhooks: `webhook-id`, `webhook-timestamp`,
  `webhook-signature` (HMAC-SHA256, secrets rotatable with overlap); exponential backoff
  with jitter for 24 h; a delivery log; SSRF-safe client (`SEC-105`); every destination in
  the egress list.
- **Function triggers (`FN-025`).** Cron schedules (in-house parser, UTC or zone) run by the
  worker's scheduler; inbound webhooks at `/hooks/<app>/<function>` verified by Standard
  Webhooks signatures or a provider-specific verifier interface (for `PAY-006` later),
  replay-protected (`PLX-7152`).

### 5.8 Telemetry ingestion and analytics (E6) — ADR-0080, ADR-0085

- **Ingestion.** The existing endpoint batches into a queue (Valkey stream), workers write
  in bulk; quotas from the registry; consent categories honoured server-side as well.
- **Storage (`ANL-010`).** PostgreSQL: monthly partitions of raw events; rollups (5-minute,
  hourly, daily) by app, release, plugin, page, device class, locale; ClickHouse adapter
  (ee) behind the same interface, with the switch-over guidance (≈ 10 M events/day or 1 M
  active devices) in the sizing guide.
- **Retention (Q17).** Raw 13 months, rollups indefinitely, production audit 10 years, all
  configurable per organisation and per data class; a change takes effect in the
  configured off-peak maintenance window (default 02:00–04:00 in the installation's zone)
  or immediately when the administrator says so; scheduled changes are visible and
  cancellable; every change is audited (`PLX-8301`).
- **Exports (`ANL-011`).** OTLP (core), signed webhooks and periodic Parquet files to object
  storage (ee).
- **Dashboards (`ANL-020`).** Grafana dashboards over a Plux datasource API (or directly
  over the PostgreSQL rollups): organisation overview, app overview (active devices,
  sessions, release adoption), page and plugin usage, funnels, crash-free sessions and
  error rates per release/plugin/page, performance (build time and jank percentiles by
  device class), sync health, function latency and errors, experiments, `l10n_missing`.
- **Alerts (`ANL-030`).** Rules on any dashboard metric, evaluated by the worker, routed to
  E7 channels; Prometheus rules for infrastructure alerts (`OBS-004`).
- **Errors (`ANL-040`).** Fingerprint = error code + JSON path + top frames; symbolicated
  through the release's retained source maps (`CMP-041`); grouped views and trends.

### 5.9 Audit, reconstruction, data subjects, egress (E8) — ADR-0082

- **SIEM export (`SEC-143`).** Syslog RFC 5424 over TLS (core); CEF, OTLP logs and signed
  webhooks (ee); at-least-once with a cursor; retention per §5.8.
- **Reconstruction (`SEC-142`, Q14).** Given app, device or user ID and a timestamp, the
  server resolves the release active then (from device sync reports, already recorded),
  the bundle hashes loaded, the control document, flags and experiment assignments in
  force, locale, theme, text scale and device class. It packages them as a **reconstruction
  release**: a signed, read-only release on a dedicated `audit` channel that contains the
  retained bundles exactly as shipped plus a reconstruction manifest (route, parameters,
  recorded state the runtime may keep; no personal data unless retained under consent).
  The `auditor` role (permission `reconstruction.view`) opens it on a device or emulator
  through the **viewer host** (`apps/plux_viewer`, a minimal host P10 grows into the Dev
  app), which runs the runtime in reconstruction mode: no network beyond the server, no
  actions with side effects, a banner naming the reconstructed moment. Every view is
  audited. `PLX-8502` when the bundles are no longer retained.
- **Data subjects (`SEC-162`).** Export (JSON archive) and erase for a device or
  pseudonymous user ID across events, rollup contributions, device records, function logs
  and outbox metadata; a generated personal-data map (where each field is stored and for
  how long); erasure is audited and leaves tombstones only.
- **Egress (`SEC-163`).** All outbound calls go through one egress client that refuses
  destinations not configured (attestation, AI provider, push, webhooks, SIEM, SMTP,
  OTLP, Git remotes); the generated egress list (`docs/operations/egress.md`) is checked
  in CI against the code's registry of destinations.
- **Search (`SRV-061`).** PostgreSQL full-text indexes over apps, plugins, pages,
  components, templates, translation keys and functions; results filtered by the caller's
  permissions in SQL (row-level security), never after fetching.
- **Git export and import (`GOV-011`).** On every publish (setting per app), the worker
  writes the `SCH-006` layout to a configured remote with server-held credentials through
  `go-git` (A1); `plux git import` brings a repository back through the normal validation.

### 5.10 Enterprise edition and licence (E10) — ADR-0084

- **Boundary (`GOV-033`).** `ee/` is its own Go module (`ee/backend`) importing the core's
  public extension points: `identity.Provider` (SAML), `scim.Server`, `governance.Stages`,
  `analytics.Store` (ClickHouse), `export.Sink` (Parquet, CEF, OTLP logs, webhooks),
  `freeze.Calendar`, `compliance.Reporter`, `airgap.Bundler`. The core registers no-op or
  community implementations; `cmd/plux-server-ee` links both. CI builds and tests the core
  without `ee/` (a dedicated job), and the `ee` image separately.
- **Licence.** D-L (§2.2). `ee/LICENSE`: the lead's draft commercial licence (source
  visible; production use requires a valid licence file; modification for own use allowed;
  no circumvention of licence checks; no offering as a service without agreement), marked
  for legal review before the first public release (open-decisions list).
- **REUSE.** `REUSE.toml` and ADR-0022 cover `ee/` with the commercial licence identifier
  (`LicenseRef-Plux-Enterprise`).

### 5.11 Operations (E9) — ADR-0083, ADR-0085

1. **Helm chart (`DEP-003`).** `deploy/helm/plux`: `api`, `worker`, `fnrunner`, `egress`,
   `builder` deployments; values schema (`values.schema.json`); NetworkPolicies isolating
   `fnrunner` and `builder` (L-4); Pod Security `restricted`; PodDisruptionBudgets; HPA;
   topology spread; secrets from existing Secrets or external secret stores; checksum
   annotations for config rollouts; `helm test` hooks.
2. **HA (`DEP-004`, Q19).** ≥ 2 replicas per role; CloudNativePG cluster (3 instances,
   synchronous replica option); Valkey with Sentinel (the P6 hand-off); SeaweedFS with
   replication or external S3; rolling upgrades with readiness gates and connection
   draining; migrations as a pre-upgrade Job that is backward compatible for one minor
   release (expand/contract), tested by upgrading mid-traffic (X5).
3. **Backups (`DEP-010`).** CloudNativePG continuous WAL archiving to object storage
   (PITR), object-storage versioning or replication, a consistency marker tying both;
   `make restore-drill` restores to a new namespace at a random point within the last hour
   and verifies manifests, bundle hashes and the audit chain (X4).
4. **Air-gapped (`DEP-040`, ee).** `plux airgap bundle` produces a signed archive of images
   (OCI layout), the chart, docs and the egress list; `plux airgap verify` and an install
   guide with a local registry; CI installs from the bundle on `kind` with networking
   denied.
5. **Observability (`OBS-004`, `OBS-005`).** Grafana dashboards and Prometheus alert rules
   in `deploy/`, each alert with a runbook link (`docs/runbooks/alerts/<name>.md`), the
   P6 runbooks' alerts included; SLOs (manifest availability 99.95%, function success
   99.9%, publish job success 99.5%, control propagation ≤ 60 s p95) as recording rules
   with burn-rate alerts.
6. **IaC (`DEP-050`, Q1).** OpenTofu modules `deploy/iac/{aws,gcp,azure}` (managed
   Kubernetes, managed PostgreSQL or CloudNativePG, object storage, Valkey, KMS for
   signing keys where the provider has one, networking), and an on-premises reference
   architecture document. **Verified without cloud accounts:** `tofu validate`,
   `tofu test` with `mock_provider` blocks asserting the planned resources, and a policy
   check (no public buckets, encryption on, private networking). Low priority: last in E9.
7. **Sizing (`DEP-051`, `NFR-023`, `NFR-040`).** A load generator (`test/load`) simulates
   devices (manifest, control, telemetry, functions) against the chart; the CI run at a
   fixed scale and the extrapolation method are documented; the maintainer's full run
   (Q20) fills the guide's top rows.

### 5.12 The audit walkthrough (exit, Q5)

`test/walkthrough/` drives the HA install on `kind` with the CLI and a synthetic device
fleet (Go clients speaking the device protocol with DPoP), and the Plux Bank app on an
emulator for the reconstruction step:

1. SSO sign-in (OIDC test provider), a custom role, SCIM provisioning of a team.
2. A release touching a `secure` page: the `maximum` policy requires two approvers from
   distinct teams; the author cannot approve; a content change invalidates an approval.
3. Staged rollout 1% → 10% → 50%; a synthetic regression trips the health gate; the
   rollout pauses and rolls back automatically.
4. Kill switch on a page through break-glass during a change freeze; the fleet applies it
   within 60 s; the post-hoc review is opened and closed.
5. A mandatory update and a forced rollback on the fleet.
6. Audit export to a syslog sink; a compliance report for the period, verified.
7. "What did the user see": the auditor reconstructs a device's moment and the viewer host
   on the emulator shows the page; the view is audited.
8. A rolling upgrade of the chart mid-run without a failed device request.
9. A data-subject export and erasure.

Each step writes evidence; the run ends with a signed evidence bundle. The written version
for auditors is `docs/compliance/walkthrough.md`.

### 5.13 Reference apps (E11, `DX-004`)

- **Plux Express:** a scheduled campaign banner via rollout schedule; an A/B experiment on
  the catalogue banner with exposure events; a flag-gated courier feature.
- **Plux Bank:** production releases under the `maximum` policy; a kill-switch drill on the
  transfer page; the reconstruction scenario of the walkthrough.

### 5.14 Runbooks and documents (E11)

Runbooks for every new failure mode (DoD-9): approval deadlock and break-glass, stuck
rollout, control-document key rotation, health-gate false positives, telemetry backlog,
ClickHouse switch-over, SIEM backlog, DSR, licence expiry, restore, upgrade rollback,
air-gapped upgrade. Guides: governance, SSO/SCIM, rollouts and experiments, analytics,
operations (Helm, HA, backup, air-gapped, IaC, sizing), compliance pack (`DX-002`).
Threat-model delta (DoD-6): federation, approvals, control role, telemetry PII, exports,
licence.

## 10. Risks

| Risk | Mitigation |
|---|---|
| Scope: about three times P8 | Strict milestones, waves of parallel agents, the `ee/` split keeps the core path short; IaC last |
| SAML XML-signature attacks | `crewjam/saml` with signed assertions required, XML-wrapping and replay tests fuzzed, audience and recipient checks |
| The control role key compromised | Online role limited to the control document, short expiry, rotation runbook, root key offline (ADR-0004) |
| Health gates rolling back healthy releases | Minimum samples, confidence bounds, pause before rollback by default, per-rollout thresholds |
| Experiment statistics misused | Always-valid sequences only, SRM gate, guardrails, documented interpretation |
| Telemetry volume on PostgreSQL | Partitioning, rollups, quotas, documented ClickHouse switch-over |
| CI minutes for `kind` and drills | Nightly and path-selected runs (Q21) |
| Kubernetes work without a cloud | `kind` for everything testable; IaC verified with mock providers |
| Licence check annoying operators | Never blocks device traffic or security; grace period; read-only, never deletion |
