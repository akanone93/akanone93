# Threat Model

The STRIDE threat model required by `SEC-000` is established in P6 and reviewed at the end of every phase from then on. Until P6, each phase records its delta here (DoD-6): what it adds to the attack surface, the threats, and the mitigations with the requirement or test that holds them.

## P1 — Schema and compiler

**Scope.** Project documents (JSON in the Git layout), the compiler and `plux validate`/`build` on developer machines and CI, the bundle format and its Go verifier, PXL programs. Nothing in P1 is networked or signed; bundles are not yet delivered to devices.

**Trust boundaries.** Documents are untrusted input to the compiler: they come from contributors, Studio users and, later, AI assistance. Bundles are untrusted input to every reader, including the runtime from P3.

| STRIDE | Threat | Mitigation | Evidence |
|---|---|---|---|
| Tampering, DoS | A crafted document crashes the compiler, exhausts memory or makes it run for long | Strict I-JSON parser, file-size, depth, string, expression and nesting limits from the registry (`LIM-001`); PXL constant folding bounded by the operation budget; panics recovered as `PLX-2201` | `FuzzCompile`, `FuzzValidatePage`, PXL and JCS fuzz targets, nightly fuzz workflow (`CMP-052`, `QA-004`) |
| Elevation of privilege | Executable code smuggled into a bundle | Only PXL bytecode and action graphs are executable; assets and unknown sections starting with native, script, Dart snapshot or WebAssembly signatures are refused; SVG scripts refused (`SEC-054`, `PLX-1503`) | `TestInvalidProjects` (executable asset, SVG script), `bundle` tests |
| Tampering, DoS | A crafted bundle exploits a reader | Section hashes, bounds and a schema-driven FlatBuffers verifier with depth and table limits before any accessor runs (`BND-006`); PXL programs verified on decode; zstd transport bounded by the declared size (`BND-007`) | `FuzzVerifyPage`, `FuzzRead`, mutation test, Dart decoder over the golden bundles |
| Information disclosure | Secrets or sensitive values end up in bundles, which are readable on devices | Secret-like literals (`PLX-1500`), sensitive state sent to analytics (`PLX-1501`), `http:` URLs (`PLX-1502`); diagnostics never repeat a suspected credential | `TestInvalidProjects`, `TestDiagnosticsDoNotEchoCredentials` |
| Tampering | Two different styles or programs share a 64-bit content ID and one silently replaces the other | A collision is a compile error (`PLX-2202`) | encoder check |
| Spoofing, Repudiation | A modified bundle is taken for a published one | Out of scope in P1: bundle hashes give integrity only. Signing and TUF metadata arrive in P2/P6 (`SEC-050`–`SEC-052`); the runtime never loads unverified bundles | — |
| Tampering (supply chain) | A compromised code generator or dependency | flatc built from source at the pinned tag commit; new dependencies allowlisted by ADR; reproducible builds (`CI-006`); goldens reproduced on three platforms (`CMP-002`) | `go-reproducible`, `go-determinism` |

**Residual risks and follow-ups (P1).** The Dart runtime's FlatBuffers verifier arrives in P3 (`SEC-052`); until then Dart only checks the container. Manifest, DPoP and attestation parsing are fuzzed from P2/P6 (`QA-004`). Regular expressions in PXL (`matches`) arrive in P5 and need a bounded engine.

## P2 — Backend core

**Scope.** `plux-server` with its api and worker roles, the ConnectRPC/HTTP API, PostgreSQL, object storage, Valkey, the durable job queue, the signing abstraction (Vault Transit and the development file backend), device registration and the manifest, deltas, telemetry intake, the `plux` CLI against a server, the Compose stack, container images and the release pipeline.

**Trust boundaries.** (1) Internet → api role: every request is untrusted — Studio users, CLI and CI callers, devices. (2) api role → PostgreSQL, S3, Valkey: trusted stores, but every tenant query runs under row-level security. (3) api role → worker: only through jobs in the database; only the worker holds a signer. (4) Server → outbound hosts (OIDC discovery, CI federation keys, malware scanner): the destination may be attacker-influenced. (5) Release pipeline → users installing images and binaries.

| STRIDE | Threat | Mitigation | Evidence |
|---|---|---|---|
| Spoofing | Password guessing or credential stuffing against Studio accounts | Argon2id, decoy hash for unknown addresses, per-account throttling (`auth.failedSignIns`), second factor (TOTP, WebAuthn) required for the capabilities of `SEC-100`, hashed challenges closing after five wrong codes | `internal/auth` tests (`SEC-100`, `SEC-101`) |
| Spoofing | A stolen session or cross-site request | `__Host-` cookies, CSRF tokens bound to the session, cookie domain refused in configuration | `internal/auth`, `internal/api` tests (`SEC-101`) |
| Spoofing | A leaked CLI or CI token | Personal access tokens with fixed scopes never above the creator's; CI federation verified against the provider's keys with installation-bounded subject patterns; tokens stored only as hashes; the CLI keeps its token in the OS credential store ([ADR-0028](../adr/0028-cli-credential-storage.md)) | `internal/auth`, `cmd/plux` tests (`SEC-102`, `CLI-002`) |
| Spoofing | A forged device or a device replaying another's token | Device secrets stored as hashes, 15-minute access tokens, device tokens open only the four device procedures. Hardware binding (DPoP, attestation) arrives in P6 | `internal/device` tests (`GOV-010`); device binding P6 |
| Elevation of privilege | One organisation reads or writes another's data | PostgreSQL row-level security on every tenant table, and the server refuses a database role that it does not bind (superuser, `BYPASSRLS`); the tenant setting is local to its transaction; RBAC checked per procedure; page tokens bound to procedure, scope, filter and order | `storage` and `tenancy` integration tests (`SRV-020`, `SRV-022`, `GOV-001`) |
| Elevation of privilege | The internet-facing api role signs arbitrary content | Only the worker role gets a signer (`CrypterOnly` for the api role, ADR-0006); signing only after a compile with no error or unacknowledged warning; the file backend refuses production environments (`SEC-056`) | `internal/signing`, `internal/release` tests (`SEC-120`) |
| Tampering | A modified bundle, delta or manifest served by a compromised CDN or store | Bundles addressed and signed by bundle hash; deltas refused when the result's hash differs (`PLX-3011`); manifests signed as RFC 8785 canonical JSON with a seven-day expiry. Device verification is P3/P6 | `delta` property and fuzz tests, `TestPublishWithTheCLIAndSyncADevice` (`REL-020`–`REL-033`, `BND-002`) |
| Tampering | A release differs from what was reviewed | Build once, promote: a release is recompiled from its versions' sources and must be byte-identical (`PLX-8050`); rollback is a new sequence with old content | `internal/release` tests (`REL-001`–`REL-007`) |
| Repudiation | An administrator denies a change | Append-only audit chain per organisation, a trigger refusing `UPDATE`/`DELETE`/`TRUNCATE`, request metadata from the edge, lock takeovers recorded with both parties | `internal/audit` tests (`SEC-140`) |
| Information disclosure | Secrets, tokens or sensitive fields in logs, traces, metrics or errors | Redacting logger by attribute name and `Sensitive` interface, fixed metric label sets, unrecognised failures become one internal error with an incident ID, telemetry fields that look sensitive refused, secrets sealed per row | `internal/observability`, `internal/api`, `internal/telemetry` tests (`SRV-006`, `SEC-106`, `OBS-001`) |
| Information disclosure | Secrets committed in documents | Secret-like literals by pattern and entropy refuse the publish (`SEC-107`) | `internal/compiler` tests |
| Tampering, Information disclosure | Server-side request forgery through OIDC discovery, federation keys or scanner addresses | SSRF-safe client checking the resolved address at dial time and on every redirect, response size limits | `internal/httpx` tests (`SEC-105`) |
| DoS | Oversized requests, floods, decompression bombs | Request, response and stream sizes and per-address, per-account and per-device rate limits from the limits registry; zstd bounded by the declared size; asset pixel and size limits; transcoders in fresh WebAssembly instances | `internal/api`, `delta`, `media` tests and `FuzzMedia` (`SEC-104`, `LIM-001`, `SRV-065`) |
| Tampering (supply chain) | A compromised image, binary or dependency reaches users | Reproducible binaries (`CI-006`), distroless images pinned by digest and running as non-root, CycloneDX SBOMs, cosign keyless signatures and SLSA level 3 provenance for images and archives; `install.sh` verifies checksums and the signature | `release.yml`, `image.yml` (`DEP-001`, `CI-004`) |
| Elevation of privilege | A container escape or lateral movement in the Compose stack | Read-only root file systems, all capabilities dropped, `no-new-privileges`, non-root users, ports bound to `127.0.0.1` | `compose.yaml`, `backend/Dockerfile` (`SEC-108`, `DEP-002`) |

**Residual risks and follow-ups (P2).** Device binding (DPoP, attestation) and the full TUF role set with rotation arrive in P6 (`SEC-050`–`SEC-056`); until then a stolen device secret works from any device, and P2 has no call to revoke one registration (device lifecycle arrives in P6). The runtime's manifest and bundle verification is P3. Studio's browser protections (nonce CSP, Trusted Types) arrive with Studio in P11. The load-test Compose overlay trusts Docker's private ranges as proxies and must never be used outside a load test. The ASVS 5.0 L2 and API Top 10 checklist for the server is in [asvs-server.md](asvs-server.md).

## P3 — Runtime rendering

**Scope.** The `plux_flutter` runtime in a host app: the sync isolate (device registration, tokens, manifest, downloads, deltas), manifest and bundle verification, the release store on the device, the memory-mapped bundle reader and first-use section checks, the renderer with PXL bindings, assets and remote images, telemetry, the Android and iOS platform code (credential store, `mmap`, zstd), the embedded baseline, and `plux_devtools`. Design: [ADR-0029](../adr/0029-on-device-verification.md), [ADR-0030](../adr/0030-native-code-in-plux-flutter.md), [ADR-0031](../adr/0031-rendering-model.md), [ADR-0034](../adr/0034-runtime-telemetry.md).

**Trust boundaries.** (1) Network → sync isolate: the server, CDN, proxies and Wi-Fi are untrusted for integrity; only the embedded `targets` keys are trusted. (2) Sync isolate → release store: nothing reaches the store before verification. (3) Store → UI isolate: the store's files can be changed by anything with access to the app's storage (a rooted device, a backup restore), so bundles are checked again on use. (4) Bundle content → renderer: a verified bundle is still authored content — it is interpreted, never executed. (5) Plugin → network: remote images reach only the domains the plugin declares. (6) Runtime → server: telemetry leaves the device only within the user's consent.

| STRIDE | Threat | Mitigation | Evidence |
|---|---|---|---|
| Tampering, Spoofing | A forged or modified manifest from a compromised server path, CDN or proxy | RFC 8785 canonical form and Ed25519 over the `targets` keys embedded at build time (`plux pull`, `PluxConfig.rootKeys`); the app, environment and channel must match; checked in the ADR-0029 order before any field is used | `manifest_test.dart` (`SEC-052`, `QA-004`) |
| Tampering | An old, validly signed manifest replayed to roll a device back to a vulnerable release | Seven-day expiry by the device clock (`PLX-3002`); the highest accepted sequence is a floor kept in the store's pointer (`PLX-3003`) | `manifest_test.dart`, `sync_engine_test.dart` (`SEC-055`) |
| Tampering | A modified bundle, delta or asset file in transit or in the CDN | The whole bundle's hash is checked against the signed manifest before it is stored; a delta's result must hash to the target (`PLX-3011`, one full-bundle retry); asset files against their signed hash (`PLX-3045`); baseline bundles against their publish signature | `bundle_verifier_test.dart`, `sync_engine_test.dart`, `baseline_test.dart`, `assets_test.dart` (`SEC-052`, `SYN-011`, `AST-001`) |
| Tampering | A bundle changed on the device after it was verified (rooted device, restored backup) | The page host checks the bundle's header against the signed release record when it maps it, and each section's hash and FlatBuffers structure before first use; a failing plugin shows its fallback and is reported once, the rest of the app renders | `runtime_test.dart` "stored bundle was tampered with" (`RT-022`, `SEC-052`, `BND-006`) |
| Elevation of privilege | Malformed input exploiting the parsers (container, FlatBuffers, zstd, delta, manifest JSON) | Nothing beyond a container header is parsed before verification (`SEC-052`); a generated FlatBuffers verifier with depth, table and size limits (`BND-006`); zstd bounded by the declared size; the delta applier's instruction and size limits; typed errors only, fuzzed against the Go corpus | `flatbuffers_verifier_test.dart`, `zstd_test.dart`, `delta_vectors_test.dart`, `bundle_verifier_test.dart` (`QA-004`) |
| Elevation of privilege | Downloaded content running code on the device | No downloaded executable code: PXL bytecode runs in a bounded interpreter (instruction, depth and size limits from the signed app bundle); events are no-ops in P3 (`PLX-4010`); unknown widgets render a placeholder (`PLX-4003`); a bundle requiring an unknown feature is refused (`PLX-3010`) | `robustness_test.dart`, `nodes_test.dart`, `sync_engine_test.dart` (`SEC-054`, `BND-008`, `WGT-014`) |
| Tampering, DoS | A crash or power loss while a release is written corrupts the store | Objects, record and pointer written in order, each `fsync`ed and renamed, the directory `fsync`ed; a checksummed pointer, corrupt ⇒ empty store and a fresh sync; the active release is never modified | `release_store_test.dart`, `kill_test.dart` (`SYN-005`, `QA-009`) |
| DoS | A bad release crashes the app on every start | Trial launches: three attributed failures within the first two launches revert to the last known good release and pin it (`PLX-3020`); kill switches per plugin and app; error boundaries around every page and component instance | `runtime_test.dart` (`SYN-006`, `RT-020`, `RT-022`) |
| DoS | A release or the telemetry buffer fills the device's storage | The disk quota of the signed limits is checked before downloading (`PLX-3030`); a full disk leaves the active release intact; the telemetry buffer is bounded (`telemetry.bufferBytes`, oldest dropped); the image disk cache is bounded | `release_store_test.dart`, `sync_engine_test.dart`, `telemetry_test.dart` (`SYN-012`, `LIM-004`, `ANL-002`) |
| DoS | A slow or hostile server stalls start-up | The UI isolate never waits on the network under the default policy (`useCacheThenSync`); downloads run on the sync isolate with bounded retries, backoff with jitter and a capped `Retry-After`; `blockUntilSynced` has a timeout | `sync_worker_test.dart`, `api_client_test.dart`, `runtime_test.dart` (`SYN-003`, `SYN-010`, `RT-004`) |
| Information disclosure, Spoofing | The device credential is read from storage and used from another device | The registration secret lives in the Android Keystore (AES key, non-exportable) or the iOS Keychain (`AfterFirstUnlockThisDeviceOnly`), never in the release store or logs; access tokens only in memory for at most 15 minutes. Binding to hardware (DPoP, attestation) arrives in P6 | Device end-to-end jobs exercise both stores (`QA-006`); device binding P6 |
| Information disclosure | Telemetry reveals personal data or what the user looks at without consent | Only the necessary events (`session_start` without locale, `sync_result`, `error` codes and node paths, never messages) without consent; everything else by category of `PluxConsent`; withdrawing consent deletes the category's buffered events; `sensitive` fields are never read into events | `telemetry_test.dart`, `runtime_telemetry_test.dart` (`ANL-003`, `SCH-012`, `SEC-161`) |
| Information disclosure, Tampering | A plugin makes the device fetch from arbitrary hosts, or plain HTTP is intercepted | Remote images only over HTTPS and only from the plugin's declared domains (`PLX-6030`), refused above `runtime.imageSize`; release builds of the reference apps forbid cleartext traffic — debug builds allow it for `make dev` only | `image_providers_test.dart`; `apps/starter/android/app/src/*/AndroidManifest.xml` |
| Elevation of privilege | The developer overlay ships in a release build | `plux_devtools` is a separate package whose overlay adds nothing in release builds (`kReleaseMode`) | `devtools_overlay_test.dart` (`RT-060`) |

**Residual risks and follow-ups (P3).** Until P6 the device credential is not bound to hardware and requests carry no DPoP proof (`SEC-020`–`SEC-025`), so a secret extracted from a rooted device works elsewhere; root-key rotation and the full TUF role set arrive in P6 (`SEC-050`, `SEC-051`), so replacing a compromised `targets` key needs a new app build. There is no certificate pinning (P6), so integrity rests on signatures, not on TLS. A device whose clock is set back can accept a manifest past its expiry; the sequence floor still prevents rollback. Layout and paint errors are contained by Flutter and reported to the host's `FlutterError.onError`, not to Plux telemetry (ADR-0031). The vendored zstd decoder is C code: it is fuzzed, built with hidden visibility, and updated only through `native/zstd/import.sh` (ADR-0030).

## P4 — Routing, host integration and no-code generation

**Scope.** The action engine core and the nine P4 actions; routing by name through the navigation delegate, with guards, deep links and push payloads; the native catalogue — native routes, slots and custom actions registered by the host, `plux native scan` and `sync`, `NativeCatalogueService` and publish validation per host build; mixed screens and the host API (`PluxView`, exposed state, plugin events); `plux codegen`, `plux init` and `plux create`; and the add-to-app module. Design: [ADR-0023](../adr/0023-mixed-screens-slots-and-plux-view.md), [ADR-0024](../adr/0024-no-code-generated-projects.md), [ADR-0039](../adr/0039-action-engine-core.md), [ADR-0040](../adr/0040-navigation-delegate-and-router-adapters.md), [ADR-0041](../adr/0041-native-catalogue-and-host-builds.md).

**Trust boundaries.** (1) Platform → runtime: deep links and notification payloads come from anywhere on the device or the network and are untrusted input. (2) Plugin → host: a verified bundle is still authored content; what it passes to the host's routes, slots and custom actions, and the events it emits, cross into code the host wrote and trusts. (3) Host → runtime: the auth delegate, user context and exposed state are the host's; Plux reads them, never stores them. (4) Developer → server: a host build's native catalogue decides which releases its devices may take. (5) Developer machine → Git remote: `plux create --git` pushes with the developer's own credentials.

| STRIDE | Threat | Mitigation | Evidence |
|---|---|---|---|
| Tampering, Elevation of privilege | A crafted deep link opens a page the user should not reach, or with values the page does not expect | A link maps only to the app's declared hosts and schemes (`https` only for hosts), through the app document's patterns or `/p/<route>`; its values are converted by the target page's parameter types, and text that does not convert shows the error fallback; malformed percent-encoding maps nothing, and resolving never throws; the target's guards run before anything is pushed | `deep_links_test.dart`: "maps nothing on another host, over http, under another scheme or for an unknown path", "never throws, whatever the link", "text that does not convert shows the error fallback" (`NAV-008`, `NAV-007`) |
| Information disclosure | A link or payload carries personal data into reports | An unmapped link is reported (`PLX-4103`) without its query; payload values reach only the page's declared parameters | `deep_links_test.dart` "a link nothing maps opens nothing and reports PLX-4103, without its query" (`SEC-092`) |
| Elevation of privilege | Reaching a guarded page another way: a link, a notification, `PluxView`, a declarative page, a shell tab, a kill switch's fallback, or a redirect loop | Guards run on every path that enters a page — `Plux.open`, `navigate`, links and payloads before the push, `PluxView`, `PluxPage` and tabs in the page's place; a guard that fails, ends without a result or navigates fails closed; redirect cycles are refused; an assurance level above `AL0` fails closed until P6; a kill switch's fallback page that is itself guarded gives way to the generic fallback (A23) | `guards_test.dart`: "an embedded PluxView runs the guards…", "a declarative PluxPage runs the guards too", "guards that redirect in a cycle are refused…", "a guard may not navigate…", "fails closed until P6"; `deep_links_test.dart` "…signed out, account redirects to login" (`NAV-009`) |
| Tampering, Elevation of privilege | A plugin passes malformed or unexpected input to the host's custom actions, native routes or slots | The compiler checks every custom action step's inputs against the native catalogue's declaration — types, unknown and missing inputs, expressions included — and every native route's parameters; the runtime converts inputs and parameters by the active release's declarations before calling host code, refuses undeclared actions, and checks outputs and results on the way back; an unregistered action, route or slot fails or shows a placeholder (`PLX-4200`–`4202`) | `TestCustomActionInputsAreChecked`; `native_catalogue_test.dart`: "a registered action runs with its checked input…", "an output of another type than the catalogue declares fails the step…", "navigate opens a registered native route with its checked parameters" (`ACT-060`, `NAV-002`, `WGT-033`) |
| Information disclosure, DoS | Host code that throws leaks the user's data into reports, or takes the page down | A failing custom action, route builder or slot is contained to its step or the node's error boundary and reported with `PLX-4205`, naming only the exception's type; runs are bounded by the limits registry's steps, step timeout and run timeout | `native_catalogue_test.dart` "…fails the step with PLX-4205, naming only its type", "…boundary and reports PLX-4205" (`RT-021`, `RT-020`) |
| Information disclosure | The user context or token reaches telemetry or plugins it was not declared for | Only attributes the app document's `userContext` declares reach expressions, typed; undeclared or ill-typed ones are reported by name only; attributes, tokens and `sensitive` fields never reach telemetry; `user.authenticated` is read from the delegate on every evaluation, never cached | `guards_test.dart` "the user context reaches guards as declared and typed…" (`HST-011`, `HST-010`, `SEC-092`) |
| Elevation of privilege, Tampering | Someone uploads or changes a host build's catalogue, so devices take releases their build cannot run, or lose ones they can | Uploading needs the publisher role; a stored catalogue never changes (the same content is accepted again, other content refused); publishing validates every plugin against the catalogues of the builds a release targets, and a build that lacks what a plugin uses keeps the last compatible release (`REL-080`) | `TestNativeCatalogues` ("only publishers upload", immutable once stored), `TestHostBuildIncompatibilities` (`CLI-006`, `WGT-032`, `REL-080`) |
| Information disclosure | `plux create` leaks the developer's Git credentials or embeds secrets in the generated project | `--git` runs the developer's own `git` as a subprocess with arguments, never a shell, using their identity and credential helpers; Plux stores nothing; the generated CI templates read keystores, certificates and store credentials by secret name, and a test scans every generated file for secret-like values; the project embeds only public root keys | `TestCreate` (`GEN-003`); `generator_test.go` (no secret in any generated file) |
| Information disclosure | `plux init` or `plux codegen` writes something sensitive into the host's sources | `plux_options.g.dart` holds the app, server, environment and public root keys; the typed API holds names and types only | `TestOptionsGolden`, `codegen_test.go` (`HST-032`, `HST-030`) |

**Residual risks and follow-ups (P4).** A custom action may not take a built-in action's name: the compiler refuses the catalogue (`PLX-1124`), since a step of that name would run the built-in instead of the host's code (maintainer, 2026-10-03). Deep links and payloads are only as safe as the app document's patterns and the target pages' parameters: a page that acts on a parameter without checking it is the author's to fix, and guards are the way to keep a page from links. `plux create --git` hands the remote and branch to `git` only after `generator.CheckGitTarget` has refused a remote that starts with `-` or holds spaces or control characters and a branch git would not accept, and puts `--` before the remote, so neither can be read as an option (some git options run commands; maintainer, 2026-10-03); P11's server uses the same check. The add-to-app hosts pass the runtime's settings over a method channel inside the app's own process; nothing secret crosses it.

## P5 — Actions, state, data, local database and animation

**Scope.** The complete action engine (every trigger and concurrency policy, retries, optimistic updates, flows, traces); the state engine with `persisted` and `secure` state and host writes; forms and validators with the `regex` and `phone` PXL groups; the data layer — REST, GraphQL, WebSocket and SSE on the runtime's own clients, the response cache, the encrypted outbox, uploads and downloads; the built-in store, the key-value store and `plux_db_drift` with SQLCipher; device and feedback actions and the approved capability set; `plux test`, `plux import` and `plux mock`; the reference apps and `test/refapi`.

**Trust boundaries.** (1) Runtime → plugin backends: requests now leave the device on a plugin's behalf, to servers Plux does not run, with the host's token. (2) Plugin → device: a verified bundle asks for the camera, files, location, scanner, clipboard and share sheet. (3) Device storage: values, cached responses, queued mutations and collections persist across restarts and users. (4) Developer machine: the CLI reads untrusted OpenAPI and GraphQL documents and signs test releases.

| STRIDE | Threat | Mitigation | Evidence |
|---|---|---|---|
| Information disclosure, Elevation of privilege | A plugin sends data to a server its app never approved | Every request and stream is checked on the data isolate against the plugin's declared `networkDomains`, over HTTPS or WSS only, before it leaves; the app's `capabilities` narrow what plugins may declare, checked at publish | `data_test.dart` "a request to an undeclared domain never leaves and is reported with PLX-5100", `streams_test.dart` "a stream to an undeclared domain never connects…", `TestCapabilitiesMustBeApproved` (`DAT-030`, `SEC-080`) |
| Elevation of privilege | A plugin uses the camera, location or files without the user's or host's consent | Device APIs are denied by default: a plugin declares each in its capabilities, the app approves it, the host installs the package and can narrow the set with `PluxConfig.allowedCapabilities`; an undeclared operation is blocked before it reaches the device and reported; the platform's own permission prompt still applies | `device_test.dart` "an undeclared device operation is blocked before it reaches the device and reported", `TestDeviceActionsNeedTheirCapability` (`SEC-080`, `SEC-102`) |
| Information disclosure | Tokens, passwords or other sensitive values reach traces, logs, telemetry or disk in the clear | Values tagged `sensitive` are redacted from traces in every build, and release builds record no values at all; `sensitive` with `persisted` is refused at compile time; `secure` state, encrypted cache entries and the outbox are sealed with AES-GCM under a per-installation key in Keystore or Keychain; the outbox stores no token and asks the delegate again on replay; the reference bank tags its password and session token | `engine_r1_test.dart` "a run records its steps; sensitive inputs and outputs are redacted", "release builds record no values at all", `state_engine_test.dart` "persisted and secure entries survive a restart, secure ones encrypted…", `outbox_test.dart` "mutations made while offline are queued encrypted…" (`SCH-012`, `SEC-092`, `ACT-031`) |
| Information disclosure | The next user of a shared device sees the previous user's data | `logout` and `Plux.wipeData` clear the plugin's state, key-value records, collections, cached responses and outbox, and cancel its detached runs | `data_test.dart` "logout and Plux.wipeData clear the cache…", `outbox_test.dart` "logout and Plux.wipeData clear the outbox…" (`DB-008`) |
| Information disclosure | A lost or rooted device exposes the local database | `plux_db_drift` opens the database with SQLCipher under a key derived from the per-installation key; under the `strict` and `maximum` profiles a plain database is refused | `drift_adapter_test.dart` "without an encrypting SQLite, `strict` and `maximum` refuse the…", `service_test.dart` "a profile that requires encryption refuses an unencrypted…", the adapter conformance suite (`DB-002`, `DB-003`) |
| Tampering, Repudiation | An offline mutation is applied twice, or applied long after it should have been | Each queued mutation carries one idempotency key on every attempt; replay is ordered per plugin; conflicts and refusals end the entry with events graphs reconcile; operations are queued only when marked `offlineCapable` | `outbox_test.dart` "a mutation that fails with the network is queued, and every attempt carries the same idempotency key", "a conflict (409, 412) and a client error end the entry…" (`DAT-020`) |
| Denial of service | A pattern, a stream, a response or a file exhausts the device | Regex patterns are a linear-time RE2 subset compiled at publish, fuzzed against Go's `regexp`; stream messages, responses, uploads, downloads, the cache, the outbox, collections and the key-value store are bounded by registry limits and fail with typed errors | `FuzzRegex`, `streams_test.dart` "a message over data.streamMessageSize closes the stream with PLX-5111…", `transfers_test.dart` "size limits come from the registry…", `outbox_test.dart` "a full outbox refuses the mutation with PLX-5120…" (`PXL-006`, `LIM-004`) |
| Denial of service | Repeated taps or events submit a payment twice or flood a backend | Widget events `drop` while their run is active by default; runs, steps, `forEach` and retries are bounded by the limits registry; retries only on the kinds a step lists | `engine_r1_test.dart` concurrency tests (`ACT-003`, `ACT-005`, `ACT-006`) |

**Residual risks and follow-ups (P5).** A WebSocket refused with `401` or `403` keeps retrying with capped backoff, since `dart:io` does not expose the status; SSE treats a `4xx` as final. Network domains are narrowed by the app only when it lists them; device APIs are always deny-by-default. Form fields cannot be tagged `sensitive`, so a password lives in its form's values in memory until the page closes; the types an operation sends and receives can be, and Plux Bank's are. Real assurance levels, secure-hardware key wrapping for the whole store and SCA arrive in P6 (`SEC-007`, `SEC-073`). Mock states are selected only in debug builds and tests; release bundles carry no mocks.

## P6 — Security hardening

From P6 this is the STRIDE model `SEC-000` requires, reviewed at the end of every phase. It covers everything P6 built: device keys and attestation, tokens and DPoP, remote security configuration, update metadata and signing backends, transport, encryption at rest and confidential bundles, the gateway and strong customer authentication, RASP and the secure UI. The [security whitepaper](whitepaper.md) explains the design; [device-trust.md](device-trust.md) says what attestation proves and how it is tested.

**Scope.** Device keys in StrongBox, the TEE or the Secure Enclave, and the key-agreement and SCA keys beside them; DPoP proofs on every device request; registration with Android Key Attestation, Play Integrity (verified locally) and App Attest; the development provider; RFC 9068 access tokens signed by a token key in `signing/`; the replay cache on Valkey with Sentinel failover; nonces; the remote security configuration and its delivery in the signed manifest; update metadata (`root`, `targets`, `snapshot`, `timestamp`) with the offline root ceremony; the PKCS#11 helper; signed audit checkpoints; TLS 1.3 and HSTS at the edge, mutual TLS between roles, certificate pinning on the device; AES-GCM encryption of local stores and confidential bundles; the gateway, the upstream registry, user-token exchange and SCA; `plux_security`; secure widgets, secure pages, masking and the inactivity lock.

**Assets.** (1) Customers' money and personal data reachable through the app. (2) The integrity of what devices run: releases, bundles, security configuration. (3) The confidentiality of release content for apps that need it. (4) Signing and wrapping keys. (5) The audit trail. (6) Users' secrets on screen and on disk.

**Attackers considered.** A network attacker (including a TLS-intercepting proxy and a compromised CDN or mirror); a malicious app or accessibility service on the same phone; the owner of a rooted device, with Frida; a user of a stolen, unlocked phone; a malicious or careless plugin author; an operator with partial permissions; an attacker who reaches an `api` replica through a bug; an attacker who reads backups or the database.

**Trust boundaries.** (1) Device → api or gateway role: a request is trusted only as far as its token, its DPoP proof by the hardware key the token is bound to, and the attestation behind the device record. (2) Platform attestation services (Google, Apple) → server: their evidence is verified offline against pinned roots and Play Console keys, never fetched per request. (3) Offline root key holders → server → device: the root is signed on the holders' machines; the server stores and serves it, devices verify it. (4) Server roles ↔ each other, PostgreSQL and Valkey: TLS required in production. (5) Device ↔ network: TLS 1.3 to a pinned Plux host. (6) Gateway → customer upstream: the destination is registered, not supplied by the device; the customer's API trusts only the server's assertion. (7) App code ↔ hostile device environment: the runtime reports what it sees; the server decides.

### Residual risks and follow-ups (P6)

1. **Attestation is proved in CI by synthetic vectors and the development provider.** `SEC-002` to `SEC-004` stay `WIP` until the maintainer's real-device check (B2 layer 3). The Kotlin and Swift code for Play Integrity, App Attest, StrongBox and Secure Enclave keys, native AES, native pinning, RASP and the secure UI is compiled and run only in CI and on devices. Apple's App Attestation root was taken from two independent Go modules (fingerprint `1C:B9:82:3B:…:C9:32`) and needs checking against Apple's page.
2. **Settings defined but not applied by the server yet.** `riskMetricMaxAL3` waits for Apple's fraud-metric receipt, so an iOS device never reaches `AL3`: the receipt call needs a JWT signed with the team's P-256 key, which no signing backend can hold or use, and a parser for Apple's signed receipt. `defaultFunctionAssurance` applies when functions arrive (P7). `attestationOutageGrace` (`SEC-009`), the replay-cache policy per environment (`SEC-023`) and Google's attestation status list (`SEC-002`) are applied.
3. **The replay fallback is weaker.** While the shared cache is down, a captured proof can be replayed once to each other replica inside the 15-second fallback window.
4. **Revocation does not ban.** A device that still passes attestation registers again with new keys after it is revoked. Raise what devices must prove (`minAssuranceForSync`, `allowSoftwareKeys`) or use the kill switch to keep a class out.
5. **An assertion can be replayed for 60 seconds** to an upstream that checks neither `jti` nor `rh`. Upstreams that move money should check both and treat `sca` as required.
6. **A rooted device that the user controls can read what is decrypted.** Confidential bundles, masked values and secure pages raise the cost; they do not hide content from the person holding an unlocked, compromised device. `plux pull` writes the plain published bundles as the embedded baseline, so content that must stay confidential should not be shipped as a baseline.
7. **Two compromised root keys require re-anchoring devices through an app release.** If both the key in use and its backup pin are lost, devices cannot reach the server until an app update ships new pins.
8. **Not pinned:** a host-supplied `httpClient`, WebSocket streams to customer domains, and calls on `direct` data sources, which the server never sees and cannot hold to an assurance level (`PLX-1504`).
9. **Local stores cannot return to a looser profile.** A `standard` launch cannot read records a stricter launch sealed and discards them. A cache entry's store time is in the clear.
10. **Android before API 31** cannot create a key-agreement key, so it receives no content keys.
11. **A local Compose stack** sends a 10-minute HSTS header so browsers keep using plain HTTP for Grafana and Prometheus on the same host.
12. **Later phases.** Function-side user claims and mTLS to `fnrunner` (P7), approvals of configuration changes, data subject export and erasure and the SIEM export (P9), Studio views and session replay consent (P11); see [plan p6](../plans/p6.md) §12.

## P7 — Plux Functions

**Status.** P7, mitigations delivered by milestones F2–F7 on `feat/phase-7`; the Evidence column names the tests that hold each mitigation.

**Scope.** Functions written in Rust, built on the server by the `builder` role, signed with the function-artifact key, and run either on the server by `fnrunner` (`wazero`) or on the device by an interpreter-only engine (WAMR, D2). Requirements: `FN-009`–`FN-013`, `FN-016`–`FN-018`, `FN-020`, `FN-021`, `FN-024`, `FN-054`.

**Assets.** (1) Tenant data in the function key-value store, one namespace per app and function (D8). (2) Secrets a function may read by name. (3) The outbound network and the reputation of the server's addresses. (4) Server availability and the fairness between tenants. (5) The integrity of function modules and of the builder and its signing handoff. (6) The decisions a server takes, which must never rest on a device's claim.

**Trust boundary.** Function code is untrusted, on the server and on the device. It is written by an app developer (or a contributor, or an AI assistant), built from source and third-party crates, and runs inside a WebAssembly sandbox with no ambient capability (`FN-012`). The boundaries are: (1) caller → `FunctionService.Invoke` on the api role, trusted only as far as its token and DPoP proof (`FN-020`); (2) api → `fnrunner`, which holds no database credentials or signing keys (L-4); (3) `fnrunner` → the network, only through `egress` (D5); (4) `fnrunner` → key-value store, only through a host call served by the api side (D8); (5) uploaded source and crates → `builder`, which has no network and no keys, and hands artifact and provenance to `signing/` through the worker (D3); (6) device module → server, never trusted as evidence (`FN-054`).

## P9 — Enterprise governance, federation, rollouts and analytics

**Status.** P9 delta (DoD-6), written in E11a-1 from the packages and specifications of the P9 milestones. The Evidence column names the Go tests that exist in the tree for each mitigation (checked by name); a row without a test name cites the requirement that holds it, and its test is still to be linked.

**Scope.** Federated sign-in and SCIM provisioning (`GOV-004`, `GOV-005`, `GOV-033`), approvals and break-glass (`GOV-020`–`GOV-024`), the online control role that signs the control document (`SYN-060`, `REL-070`), runtime telemetry and its personal data (`ANL-010`, `ANL-011`), exports to a SIEM, to signed webhooks and to a Git remote (`SEC-143`, `GOV-011`, `SEC-163`), and the enterprise licence (`GOV-030`, `GOV-032`, `DEP-040`). The control role is an online signer, separate from the root (`ADR-0077`). A SIEM, a webhook receiver and a Git remote are outside the installation: their addresses are customer-supplied and go through the SSRF-safe client. A licence file is untrusted until its signature is checked against the keys the build holds, offline.

(4) Personal data shown in Studio: members, audit entries, telemetry and session replays. (5) The build sandbox and the builder role behind the Rust editor. (6) The developer's devices paired to a dev session.

**Attackers considered.** A web attacker who controls another origin the person visits (CSRF, login CSRF, clickjacking, cross-origin reads); an attacker who gets a string into Studio's DOM (stored content in documents, names, translations, replays, language-server output, a pasted clipboard); a malicious author of a crate or function source opened in the Rust editor; a member of another organisation who crafts clipboard content or documents for copy-over; a device that sends crafted events, screenshots or node paths into a dev session; a network attacker between the browser and the BFF.

**Trust boundaries.** (1) Browser → BFF: every request is untrusted; the browser holds only the HttpOnly session cookie and an in-memory CSRF token. (2) BFF → Plux Server: the BFF holds no session state and no credential of its own beyond the OIDC state key (`PLUX_BFF_STATE_SECRET`); it forwards only the session cookie and an allowlist of headers, and the server authenticates, checks the CSRF token and authorises every call (`SEC-101`, `SEC-102`). (3) Main thread → workers: the canvas, validator, lock heartbeat and Monaco workers are Studio's own code, started only through the `plux-worker` Trusted Types policy at their hashed same-origin assets; what they parse (fonts, documents, PXL) is untrusted. (4) Server → editor: messages relayed from rust-analyzer are output of a process that reads untrusted user code, and are untrusted. (5) Clipboard → Studio: anything pasted is untrusted bytes, whoever copied it. (6) Device → Studio: events, node paths and screenshots from a paired device are untrusted.

**Residual risks (P11).** (1) `'allow-duplicates'` lets any script that already runs on Studio's origin create another `plux-worker` policy; Trusted Types guard against strings reaching sinks from Studio's own code, not against script that already executes, which the nonce CSP is there to prevent. (2) Monaco's own rendering policies pass its HTML through unchanged: Monaco is trusted for the HTML it builds from the editor's text, which it escapes. (3) `style-src-attr 'unsafe-inline'` lets injected markup set inline styles (ADR-0014 Revision 2026-10-26); no script, element or sheet comes with it. (4) `worker-src` also admits `blob:`, which no Studio code uses; Trusted Types already refuse a `blob:` worker, so this is defence in depth that is missing, not an open path (proposal in [asvs-studio.md](asvs-studio.md#gaps)). (5) The CSRF token is readable by script on the origin by design; an XSS can act as the person while the page is open, which is why the controls above aim at preventing the XSS. (6) The ZAP baseline is passive: it reports headers and cookies, not logic flaws, which the unit and end-to-end tests cover.
